## 現在地 (2026-09 時点)

対象: 僕の夏休み2 (PS2 / SCPS-15026)。吸い出し済みフォルダを構造探査台で解析中。

判明済み:

- ルート `SYSTEM.CNF` → 本体 `SCPS_150.26` (ELF32 / MIPS R5900) を逆アセンブル可能に
- `BOKU2.IDX` は独自形式 **"DFI"**。構造を逆アセンブルとバイト解析から確定:
  - ヘッダ 16 バイト (`DFI\0` + 版 0x100)
  - レコード 16 バイト: +4 名前位置 / +8 セクタ番号(×2048) / +12 長さ(バイト)
  - 本体プログラム 0x001293D8 の関数が「先頭が DFI ならバッファ+0x10 を先頭とする」
    と書いていたのと一致
- 索引を読んで `BOKU2.IMG` を **1951 ファイルに切り分け**られた
- 切り分けた先頭のかたまりは全部 `TIM2` (画像)。`00diary` の日記写真 (`nik***.tm2`)

## 最大の発見: 先行事例のソースが公開されていた (壁の正体の訂正)

**英語翻訳パッチが既に存在する** (Hilltop Works, 2023年11月公開、約 5,000 行)。
報道記事からは「独自の圧縮を書いた」「縦書き」としか分からなかったが、
**ツールのソースが GitHub で公開されていた** (HilltopWorks/BokuNoNatsuyasumi2:
`UNPACK.py` / `MSG.py` / `textCompaction.py` / `asm_notes.txt`)。読んで分かったこと:

1. **テキストは圧縮されていない。** 記事の「圧縮」は、英訳を元の容量に収める
   ために向こうが書いた **文字列の詰め込み (textCompaction.py)** のこと。
   ディスク上の `.msg` は素の「件数 + 位置表 + 本文」。
2. **文字コードはフォント画像の並び順。** 本文は 2 バイトの並びで、値は
   `bk_font.tms` の何番目の文字か (1 行 17 文字、`asm_notes.txt` の `char%17`)。
   制御コードは `0x8000` 終わり / `0x8001` 改行 / `0x8002 + u16` 待ち /
   `0xCDCD` 詰め物。**Shift-JIS ではないから、生検索で出なかった。**
   → これは docs/03 で教えている「テーブル」の実物そのもの。
3. **索引 (DFI) の名前は、レコードの直後に順番どおりに並ぶ**だけだった。
   +4 の値は名前の位置ではない (向こうも読むだけで使っていない)。
   先頭は根 "/"。+2 の u16 は「同じフォルダにまだ続くか」で、フォルダの
   入れ子はこれで復元できる (フォルダで 0 なら、それが親の最後の項目)。→ **`#N` 表示の宿題はこれで解けた。ユーザーの
   バイト提供を待つ必要が無くなった。**
4. `.msg` の位置表は IMG 内のものが 8 バイト刻み、マップ内の表が 4 バイト刻み。
   マップ (`map/*.*`) は `[u32 0xE][u32 表の長さ 0x80]` + (位置, 長さ) の対の入れ物で、
   その 1 番のファイルに `[u32 表の数][0xC の項目]` で会話の表が入る。
5. 縦書きは **表示ルーチン側** の話 (向こうは MIPS を書き換えて横書きにした)。
   データの並びは素直。

ファイルや訳文はこのリポジトリに入れていない):

## この発見が意味すること

- **PCSX2 のメモリダンプは不要になった。** ディスク上の `.msg` をそのまま読める。
- 学習の本題 (テーブル作り → 抽出 → 校正) に、実物でそのまま入れる。
- 以前の記述「テキストは圧縮」は誤り。LZSS の道具は一般用として残す。

## 次の一手 (優先順)

1. **索引タブで切り分け → 一覧の絞り込みに `msg` と入れる。** 名前が
   `system/system.msg` のように出るはず。出なければ `#N.種類` に戻るので報告。
2. **`system.msg` などを選び、「既知の形式」→「.msg として読む」。**
   件数と各行の 2 バイト番号が並ぶ。番号の最大値がフォントの文字数の目安。
3. **`bk_font.tms` を選び「既知の形式」タブで「文字の番号を重ねる」** (1 字 23 ドット、
   1 行 17 字)。番号順に文字を書き出して .msg 読みの欄に貼ると、日本語で読める。
   これが「テーブル作り」。
4. **物語の会話は `MAP` フォルダ。** `MAP/M_A11000.*` のようなファイルを選び、
   「既知の形式」→「マップの入れ物を切り分ける」→ `1.bin` を選んで「.msg として読む」。
   `0.bin` はイベントの命令列 (会話ではない)。
5. 読めたら **「校正用の TSV をコピー」** → ファイルに貼って
   `python3 tools/proofread.py そのファイル --no-font-check`。docs/04 の校正の練習へ。
6. 画面で確かめた読み方が合っていたら、**全部を一括で**:
   `python3 tools/boku2.py unpack BOKU2.IDX BOKU2.IMG OUT/` →
   `python3 tools/boku2.py maps MAP/*.* -o OUT/maps` →
   `python3 tools/boku2.py text OUT/system/*.msg OUT/maps/*/1.bin -f font.txt -o all.tsv`
   (font.txt は文字表を保存したもの)。
6. (任意) PCSX2 は「動いている状態の確認」用に残す。必須ではない。

### #8 — 全部のテキストを一括で取り出す道具 (tools/boku2.py)

- 辛口ユーザー: 「画面で 1 ファイルずつ読むのは、マップが何十個もあると
  終わらない。5,000 行を全部 TSV にしたい」
- 辛口クリエイター: 「ブラウザの読み方が正しいなら、同じ規則を Python に写して
  一括処理にできる。二つの実装が同じ答えを出すことがそのまま検証になる」
- 対応: **`tools/boku2.py`** を追加 (unpack / maps / text / fontlist)。
  - `unpack BOKU2.IDX BOKU2.IMG OUT/` で索引どおりにフォルダ付きで切り分け
  - `maps MAP/*.* -o OUT/maps` で入れ物を部品に
  - `text ファイル… -f font.txt -o all.tsv` で会話を校正用 TSV に。入れ物・表の一覧・
    単体 .msg を自動で見分け、id は `ファイル名:表-行`
  - `fontlist font.txt -o font_chars.txt` で文字表を校正ツールのフォント一覧に
    → `proofread.py all.tsv --font-chars font_chars.txt` でフォントに無い文字の検査まで通る
  - テスト: 実物と同じ形の合成データ (入れ子のフォルダ・空フォルダ規則・音声つきの
    表・入れ物) で unpack → maps → text → proofread を通し、**索引の読みは Node
    (ブラウザ側) と Python が同じ答えを出す**ことを突き合わせた。
- 次に見るべきこと: 実データで `unpack` の件数 (画面と同じ 1951 前後) と、
  `maps` が MAP フォルダの全ファイルで通るか。通らないファイルがあれば
  その先頭 16 バイトが次の手がかり。

### #7 — 読めたテキストを校正の工程へ渡せるようにした

- 辛口ユーザー: 「読めても、その先が無い。docs/04 の校正ツールは TSV を要求
  するのに、画面から TSV を作る手段が無い。文字表も読み直すと消える」
- 辛口クリエイター: 「学習の本題は校正。抽出 → TSV → proofread がつながって
  初めて教材として成立する。あと音声の項目 (8 桁の数字) が文字化けして見える」
- 対応:

    と同じ。貼って `python3 tools/proofread.py 〜.tsv --no-font-check` でそのまま校正できる。

  - 音声の項目 (8 桁の数字 ASCII、公開ソースの `isVoice` と同じ判定) を
    `{VOICE 01234567}` と表示。
  - フォントの文字表を端末内 (localStorage) に覚えておく。読み直しても消えない。
- 次に見るべきこと: 実データで `.msg` を読み、TSV → proofread まで通した結果。

### #6 — TIM2 を正しく描き、フォントに文字番号を重ねられるようにした

- 辛口ユーザー: 「文字表を作れと言われても、フォント画像が『見つけた絵』の
  推定表示ではぼやけて読めない。番号も自分で数えるのは無理」
- 辛口クリエイター: 「`.tm2` は PS2 の標準形式 TIM2 で、仕様は公開されている。
  推定ではなく **そのまま読む** べき段階 (解析の五段階目)」
- 対応:
  - **TIM2 の読み取り** `parseTim2` / `decodeTim2` を追加。32/24/16bit 直接色、
    8bit 索引 (GS の CSM1 並び替えつき) と 4bit 索引、128 バイト揃えの見出し、
    `.tms` の 0x80 前置きに対応。透明度は PS2 流 (0x80 = 不透明) を表示用に伸ばす。
  - 「既知の形式」タブで TIM2 を市松の上に描き、**「文字の番号を重ねる」**で
    1 文字の幅・高さ・余白を指定して番号を振れる。番号 = .msg の文字番号。
  - `tools/make_tim2.py` で各画素形式の試験画像と練習用フォント (`work/FONT.TM2`,
    `.TMS`) を組み立て、Python と Node の両方で突き合わせ。ブラウザでも描画を確認。
- 次に見るべきこと: 実データの `bk_font.tms` の 1 文字の大きさ (公開ソースの
  `asm_notes.txt` では 0x17 = 23 ドット、行は 17 字)。合わなければ余白と幅を調整。

### #5 — 物語の会話がある場所 (MAP の入れ物) を読めるようにした

- 辛口ユーザー: 「`.msg` を読めても、出てくるのはメニューの文言だけ。物語の
  会話 (5,000 行の本体) はどこ?」
- 辛口クリエイター: 「公開ソースには MAP の入れ物と表が複数の会話ファイルの
  読み方まで書いてある。読み残しがある」
- 対応 (公開ソースの `unpackMap` / `unpackMapMSG` / `readMSG(MAP_MODE)` に合わせた):
  - **マップの入れ物** `parseBokuMap`: `u32 項目数` + `(u32 位置, u32 長さ)` の表
    (まれに 12 バイト刻み)。位置 0 は空。部品は 16 バイト揃え。
    「既知の形式」タブの「マップの入れ物を切り分ける」で `0.bin, 1.bin…` にする。
  - **表が複数の会話ファイル** `parseBokuMsgTables`: `u32 表の数` + 12 バイトの
    項目 (u16 表の長さ / u16 番号 / u16 表の位置) + 各表 (4 バイト刻みの .msg)。
    「.msg として読む」が自動でこちらも試し、`表-行` の番号で一覧にする。
  - テスト: 合成データで 入れ物 → 1.bin → 表 2 つ → 復号 まで通し
    (node と ヘッドレスブラウザの両方)。
- 次に見るべきこと: 実データの `MAP/M_A11000.*` などで 1.bin が本当に会話か。
  公開ソースの `MAP_SCRIPTS/M_A11000.txt` は 0 番 (スクリプト命令列: PROG /
  JMPM / MAP / WAT / ANM …) の解読結果なので、0 番はイベントスクリプトと分かっている。

### #4 — 進捗確認: 先行事例のソースを読み、壁の正体を訂正

- 進捗確認 (30 分ごとの規則): #1〜#3 は道具を増やしたが、**肝心のテキストには
  一歩も近づいていなかった**。原因は「実データが手元に無いのに、当てずっぽうで
  道具を作っていた」こと。名前解決は 6 回直しても実データで外れ続けた。
- 規則どおり外部を当たり直した → **Hilltop Works のツールのソースが公開されて
  いた**。読んだ結果、(a) テキストは圧縮ではなくフォント順の 2 バイト符号、
  (b) 索引の名前はレコード直後に順番どおり、と判明 (上の「最大の発見」を全面訂正)。
- 対応:
  - `readDfi` を公開ソースと同じ規則に書き換え (名前を順番に読む・フォルダの
    入れ子を復元・名前が壊れていれば `#N`)。テストの索引も実物の形に作り直した。
  - **`.msg` 読み** (`parseBokuMsg` / `bokuMsgText`) を「既知の形式」タブに追加。
    件数・位置表・制御コードを解釈し、フォントの並びを貼れば日本語で読める。
  - 説明文の「テキストは圧縮」を訂正。LZSS は一般用の道具として残す。
- ループの適正について: 25 分の session 内 cron はコンテナのリセットのたびに
  消え (2 回消失)、自走が止まっていた。→ **サーバー側の Routine (毎時、この
  セッションに戻ってくる)** に置き換える。5 分刻みの評価は現実には 1 回 30〜60 分
  かかるので、毎時 1 回「評価 → 改善 1 件 → テスト → push → 記録」に統一する。

### #3 — 名前が無くても `.msg` の候補に辿り着けるように

- 辛口ユーザー: 「切り分けた 1951 個が `#0 #1 …` の番号だけ。`msg` で探しても
  出ない。一覧に絞り込み欄すら無い」
- 辛口クリエイター: 「名前解決はユーザーのバイト提供待ちで止まっている。
  待つ間に **名前に頼らない道** を作らないと、この宿題が全体を止める」
- 対応:
  - **中身から種類を付ける `sniffKind`** を追加。魔法数 (TIM2 / VAGp / RXWS /
    SShd / ELF / MPEG / DFI / RIFF / PNG) で確実に当て、無ければバイトの性質から
    見当を付ける。番号だけの名前には `#0012.tm2` のように末尾へ付く。
  - **圧縮の見当**: 先頭 u32 が「自分より大きく 32 倍以内」なら伸張後の大きさと
    見て `packed`。圧縮テキストのゲームでは `.msg` はここにある見込み。
  - 切り分け後に「中身の見当: tm2 1200 · packed 400 …」と集計を表示。
  - **ファイル一覧に絞り込み欄** (`msg` / `packed` / `.tm2`、空白区切りで AND)。
  - テスト: `tests/test_sniff.mjs` (魔法数 8 種・圧縮の見当・性質・集計) と
    ヘッドレスブラウザで PACK.IDX/IMG を切り分け → 22 件全部に種類が付き、
    絞り込みが効くことを確認。
- 次に見るべきこと: 実データで `packed` の件数と大きさの分布。数十 KB 台の
  `packed` が数百個なら、それが `.msg` 群 (会話ファイル) の可能性が高い。
