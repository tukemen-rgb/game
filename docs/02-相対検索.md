# 相対検索 — 未知の文字コードから日本語を探す

文字テーブルが分からないファイルから、日本語の文章を見つける方法です。
Monkey-Moore などのツールがやっているのはこれです。

## 原理

ほとんどのゲームは、フォントを「あいうえお…」の五十音順に並べます。
並べれば文字コードも連番になります。すると、

```
「こんなところ」 の各文字が並びの何番目か:
  こ = 18,  ん = 82,  な = 41,  と = 39,  こ = 18,  ろ = 76      (Unicode 順)

隣どうしの差:
  +64, -41, -2, -21, +58
```

この **差の並び** は、コードの起点がどこであっても変わりません。
「こ」が `0x13` から始まろうが `0x82B1` から始まろうが、差は同じです。

だから「差の並びが一致するバイト列」を探せば、起点が未知でも文章が見つかります。
そして見つかった位置の先頭バイトから逆算すれば、**そのままテーブルになります。**

## やってみる

```bash
python3 tools/relative_search.py work/MSG_ENC.BIN --search こんなところ
```

```
検索語 'こんなところ' の差の並び: +64, -41, -2, -21, +58
work/MSG_ENC.BIN (1,448 バイト) → ヒット 1 件

  0x00113  先頭文字 'こ' = 0x13  → 'ぁ' = 0x01 と推定
           <WAIT>⏎<NAME><VAR>・・こんなところにいたのね・<BR>ずいぶん・ぷしたのよ・<WAIT>
```

「ぁ = 0x01」まで一気に分かりました。プレビューでかなが読めているので
仮説は正しいと判断できます。読めていない `・` は漢字や記号 (まだテーブルに
入っていない部分) です。

推定したテーブルをファイルに落として、そこから育てていきます。

```bash
python3 tools/relative_search.py work/MSG_ENC.BIN --search こんなところ \
    --derive work/my_guess.tbl
python3 tools/hexdump.py work/MSG_ENC.BIN --table work/my_guess.tbl --message 2
```

あとは 16 進表示を見ながら、`・` になっているバイトに対応する文字を
手で `.tbl` に足していく作業です。地味ですがこれが本体です。
`answers/custom.tbl` と比べれば答え合わせができます。

## うまくいかないときの手順

相対検索が空振りするのは珍しくありません。原因はだいたい次のどれかです。

### 1. 検索語に濁点・小書き文字・漢字が入っている

`が` `ぱ` `っ` `ゃ` は、フォントの並びから外されていたり、別の場所に
まとめられていたりします。漢字と記号は連番ではありません。

**清音のひらがなだけ** で 4〜6 文字の語を選ぶのがコツです。汎用性の高い語:

```
ここは / たたかい / まちのひと / にげられない / おうさま / たすけて
```

### 2. 小書き文字が並びから抜けている

「ぁぃぅぇぉっゃゅょゎ」を詰めた並びを仮定します。

```bash
python3 tools/relative_search.py FILE --search ここは --order nosmall
```

### 3. 1 文字が 2 バイトである

Shift-JIS や独自の 2 バイトコードの場合です。

```bash
python3 tools/relative_search.py work/SCRIPT.BIN --search こんなところ --width 2 --endian be
```

Shift-JIS のかなは 2 バイト・ビッグエンディアン相当で連番になっているので、
これでヒットします。逆に、独自の 2 バイトコードならリトルエンディアン
(`--endian le`) のこともあります。両方試します。

### 4. テキストが圧縮されている

差の並びがどう頑張っても出てこない場合、テキストが圧縮 (LZ 系など) されている
可能性があります。これは相対検索の外側の話で、伸張ルーチンを解析するか、
エミュレータのメモリ上で展開後のテキストを探す方向になります。
初学の段階では「圧縮されていない題材を選ぶ」のが正解です。

## 偶然の一致について

差の並びは短いほど偶然一致します。3 文字だと 1 バイトコードで
数十件ヒットすることもあります。ヒットが多いときは検索語を長くします。
逆に 1 件だけ出てプレビューが日本語として読めるなら、ほぼ確定です。

## 実務との関係

業務のローカライズ QA でこの技術を使う機会はまずありません
(開発元から正規のテキストが来ます)。それでも押さえる価値があるのは、
「文字コードとは並びの規則である」という感覚が身につくからです。
それが分かっていると、実務で

* 文字化けの報告を受けたときに、エンコード違いかフォント欠落か切り分けられる
* 「この文字は使えません」という開発側の返答の理由が理解できる

という判断ができるようになります。
