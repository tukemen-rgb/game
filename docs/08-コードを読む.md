# コードを読む — PS2 の本体プログラムを逆アセンブルする

ここまでの道具はすべて「**データがどこにあるか**」を見るものでした。
このページは「**そのデータをプログラムがどう読んでいるか**」の話です。

データの構造だけを見ていて行き止まりになる場面が、必ず来ます。

* 圧縮されていて中身に届かない
* 索引の形が総当たりでは当たらない
* 文字列は見つかったが、ゲーム内のどこで使われるのか分からない

どれも答えは同じ場所にあります。**本体プログラムの中**です。
伸張ルーチンも、索引の読み方も、文字列の使い道も、コードにしか書かれていません。

## PS2 の本体プログラムとは

ディスクのルートに `SYSTEM.CNF` という小さな ASCII のファイルがあり、
中身はこうなっています。

```
BOOT2 = cdrom0:\SLPS_900.99;1
VER = 1.00
VMODE = NTSC
```

`BOOT2` が指しているファイルが本体プログラムです。名前はタイトル固有の型番で、
`SLPS_` (ソニー・日本)、`SCPS_` (ソニー製・日本)、`SLES_` (欧州) などで始まります。
このファイルの先頭 4 バイトは `7F 45 4C 46` — **ELF** です。

| 項目 | PS2 の場合 |
| --- | --- |
| 形式 | ELF32 |
| バイト順 | リトルエンディアン |
| CPU | MIPS R5900 (MIPS III + Sony 独自拡張) |
| 命令長 | **必ず 4 バイト固定** |
| よくある載せ先 | `0x00100000` |

**命令長が固定**というのが、この話の全体を易しくしています。x86 のように
命令の長さが 1〜15 バイトと変わる CPU では「どこから読み始めるか」で
まったく違う解釈になりますが、MIPS では 4 バイトずつ切って表を引くだけです。
逆アセンブラが数百行で書けるのは、そのためです。

## ELF が持っている情報

ELF は「**ファイルのこの部分を、メモリのこの番地に載せて、ここから実行しろ**」
という指示書です。読むべきは 2 つだけです。

* **入口 (entry)** — 最初に実行される命令の番地
* **読み込み区画 (PT_LOAD)** — ファイル内の位置 → メモリ上の番地の対応表

この対応表が要ります。コードの中に出てくるアドレスは**メモリ上の番地**なので、
それをファイルの中のどこかに戻すには必ずこの表を通します。
探査台の `vaddrToOffset()` と `elfdump.py` の `Elf.to_offset()` がそれです。

セクション (`.text` = 命令、`.rodata` = 文字列や定数、`.data` = 変数、
`.bss` = ファイルに実体の無い領域) は付いていれば読みますが、
**製品版では削られていることも多い**ので、無くても困らない作りにしてあります。

## MIPS の命令の読み方

覚えることは驚くほど少ないです。

| 記号 | 意味 |
| --- | --- |
| `$a0`〜`$a3` | 関数の引数 (1〜4 番目) |
| `$v0`, `$v1` | 戻り値 |
| `$sp` | スタックポインタ |
| `$ra` | 戻り先アドレス |
| `$zero` | 常に 0 |

読むときの目印:

* `addiu $sp, $sp, -N` と `sw $ra, ...` が並んだら、そこが**関数の入口**
* `jal 0x...` が**関数呼び出し**、`jr $ra` が**関数の終わり**
* `lw` が読み込み、`sw` が書き込み、`beq` / `bne` が条件分岐

### 遅延スロット

MIPS 特有の癖が 1 つあります。**分岐命令の次の 1 命令は、分岐が成立しても
必ず実行されます。** これを遅延スロットといいます。

```
0010003C  jr    $ra              ← 戻る
00100040  addiu $sp, $sp, 0x20   ← でもこれは戻る前に実行される
```

知らないと「戻ったあとの命令が動くわけがない」と混乱します。
探査台は遅延スロットに印を付けて出します。

### 32 ビットのアドレスは 2 命令に割れる

命令が 4 バイト固定ということは、**32 ビットの即値を 1 命令に入れられない**
ということでもあります。だからアドレスは必ずこう分かれます。

```
0010000C  lui   $a0, 0x10             上位 16 ビットを置く
00100010  addiu $a0, $a0, 0x414       下位 16 ビットを足す  → 0x00100414
```

この組を追いかけると、コードが指しているアドレスが復元できます。
そこに文字列があれば、**どの文字列をどこで使っているか**が分かります。
これが実務でいちばん効く一手です。

なお `addiu` は**符号付き**で足すので、下位 16 ビットの最上位が立っていると
上位側が 1 繰り上がっています (`0x1234FF00` なら `lui 0x1235` + `addiu -0x100`)。
ここを間違えると復元したアドレスが 0x10000 ずれます。
`tools/make_elf.py` の `hi_lo()` が、この繰り上げをわざと仕込んであります。

## 探査台での操作

「逆アセンブル」タブです。ELF でないファイルを選んでいるときは、
何を選べばいいかを出します (本体プログラムらしい名前のファイルがあれば
そのまま押せます)。

1. **入口から読む** — 開いた時点で entry から 256 命令が出ています
2. **飛ぶ** — `jal` や `beq` の行き先はクリックできます。「← 戻る」で戻れます
3. **文字列を使っている場所を全部探す** — コード全体を走査して、
   `lui` + `addiu` の組から文字列を指しているところを一覧にします

3 番から始めるのが早いです。目当ての言葉がどこで使われているかが分かれば、
読むべき関数が決まります。1 命令ずつ順番に読む必要はありません。

## コマンドラインでの操作

```
# ヘッダと区画
python3 tools/elfdump.py work/BOOT.ELF

# 入口から 64 命令
python3 tools/elfdump.py work/BOOT.ELF --disasm --count 64

# 指定した番地から
python3 tools/elfdump.py work/BOOT.ELF --disasm --addr 0x00100100

# 文字列の参照を全部
python3 tools/elfdump.py work/BOOT.ELF --xref
```

練習用の本体プログラムは `python3 tools/make_elf.py` で作れます。答え
(入口・関数の位置・仕込んだ文字列) が実行時に表示されるので、
探査台の出す結果と突き合わせられます。`tools/make_iso.py` はこれを
`SLPS_900.99` としてイメージのルートに入れるので、
**SYSTEM.CNF → BOOT2 → 本体プログラム → 逆アセンブル**という
実物とまったく同じ順路を、権利の問題なしに一通り辿れます。

## 自分で書いた逆アセンブラをどう信用するか

ここは正直に書いておきます。**自分で書いた逆アセンブラの正しさは、
自分では確かめられません。** 表を 1 つ間違えても、それらしい出力が出ます。

だから外の実装と突き合わせています。

```
pip install capstone
python3 tests/gen_mips_cases.py     # capstone の答えを固める
python3 tests/run_tests.py          # Python 側を突き合わせる
node tests/test_disasm.mjs          # ブラウザ側を突き合わせる
```

2,400 通りほどの命令語について、capstone の出したニーモニックと 1 つずつ
比べます。食い違いを許すのは 2 種類だけです。

* **R5900 独自命令** — capstone は MIPS32 として読むので、
  `lq` / `sq` (128 ビット転送) と `lqc2` / `sqc2` (VU0 との転送) は
  食い違って正しい。オペコード単位で除外しています
* **未実装** — `.word` と出しているもの。
  **知らない命令を知らないと言うのは正しい態度で、嘘の命令名を出すのが駄目**です。
  テストはこの区別をしています

## ここでも止まる壁

逆アセンブルできても、**読めるとは限りません。**

* 変数名も関数名も残っていません (`sub_100100` のような番地しかない)
* 最適化で、元のソースの形はほとんど残っていません
* 数百 KB のコードから目当ての関数を探すのは、それ自体が仕事です

だから「文字列の参照から入る」のが定石です。エラーメッセージやファイル名は
**人間が読むために書かれた唯一の手がかり**で、これが残っている限り、
そこから関数へ辿れます。

## 本気でやるなら使う外部ツール

このリポジトリの道具は**学習用**です。仕組みを分かった上で本格的に読むなら、
定番の道具のほうが圧倒的に速い。正直に並べておきます。

| 道具 | できること | 向いている場面 |
| --- | --- | --- |
| **Ghidra** (無料 / NSA) | 逆アセンブル + **逆コンパイル** (C 風の疑似コードにする)。MIPS 対応。名前や型を付けて保存できる | 腰を据えて解析する。**まずこれ** |
| **PCSX2 のデバッガ** | エミュレータ上で実際に動かし、ブレークポイント・メモリ閲覧・ステップ実行 | **圧縮を解くより速い**。展開後のメモリをそのまま見られる |
| **IDA Pro / IDA Free** | Ghidra と同系。業界標準 | 職場で使われていることが多い |
| **radare2 / rizin** | コマンドラインの解析環境。スクリプトが書きやすい | 自動化・一括処理 |
| **objdump / capstone** | 逆アセンブルだけ。軽い | 自分のツールに組み込む |

とくに **PCSX2 のデバッガ**は強調しておきます。圧縮されたデータを
ディスクから解くのは大仕事ですが、ゲームを動かせば CPU が勝手に展開して
メモリに置いてくれます。そのメモリをダンプして探査台に読み込ませれば、
**展開済みのテキストや画像がそのまま見つかります。**

「ディスクから読む」より「メモリから読む」ほうが近道になる、というのは
この分野ではよくある逆転です。
→ [05-実物のディスクを扱う場合.md](05-実物のディスクを扱う場合.md)

## 法律のこと

技術の話とは別に、ここは押さえておく必要があります。日本の著作権法では、
自分が持っているソフトであっても**コピーガードを回避した複製は私的目的でも
違法になり得ます。** 取り出したデータの配布や、改変したものの公開は明確に
問題になります。最終的な判断は専門家に確認してください。

**「技術的にできる」と「やってよい」は別問題です。**
このページの内容は、`tools/make_elf.py` が作る自作の ELF で全部練習できます。
