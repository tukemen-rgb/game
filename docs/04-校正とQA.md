# 校正とローカライズ QA

ここが実務の本体です。テキストを取り出せるようになったあと、何を見るのか。

ゲームの校正が一般の文章校正と違うのは、**「正しい日本語かどうか」だけでは
判定できない** ところです。表示枠に入るか、フォントにその字があるか、
変数が生きているか — データ側の制約を同時に見る必要があります。

## 機械で落とせるものは機械で落とす

人間が読む前に、機械的なチェックを全部通します。人間の目を残しておくのは
口調・文脈・訳の質といった、機械にできない部分のためです。

```bash
python3 tools/proofread.py exercises/qa_target.tsv
```

`tools/proofread.py` が見ている項目です。

| 分類 | 重大度 | 何が起きるか |
| --- | --- | --- |
| `placeholder` | ERROR | `<VAR:xx>` `<NAME:xx>` の欠落・改変。実機で表示が壊れる |
| `control` | WARN | `<WAIT>` `<COLOR:xx>` の欠落・増加。演出が変わる |
| `font` | ERROR | フォントに無い文字。実機で □ になる |
| `halfwidth` | ERROR | 日本語文中の半角文字・半角カナ |
| `line_width` | ERROR | 1 行の表示幅オーバー。枠からはみ出す |
| `line_count` | ERROR | 1 ページの行数オーバー。下の行が切れる |
| `kinsoku` | WARN | 行頭・行末の禁則違反 |
| `glossary` | ERROR / WARN | 用語集の誤表記、正式表記の消失 |
| `notation` | ERROR / WARN | 表記ルール違反 (`data/rules.json`。どちらになるかは設定の `severity` 次第) |
| `number` | ERROR | 原文と訳文で数字が違う。金額・ダメージ・個数の取り違え |
| `consistency` | WARN | 同じ原文が別の訳になっている (訳ぶれ) |
| `empty` | ERROR | 訳文にタグしか残っていない (本文だけが消えた) |
| `untranslated` | WARN | 訳文の欄が空 (原文がそのまま実機に出る) |
| `room` | WARN / ERROR | 訳文が**原文の入れ物 (`size` の欄) に入らない**。実機に入れる段になって詰まる |

`<BR>` の増減そのものは指摘しません。行の折り返しを調整するのは校正者の
仕事なので、代わりに `line_width` / `line_count` で結果だけを見ます。

## 仕様は数字で受け取る

`data/rules.json` の先頭 2 項目が、案件開始時に開発元から受け取るべき数字です。

```json
"line_max_width": 18.0,
"lines_max": 3,
```

「1 行 18 文字・1 ページ 3 行」。これが分からないまま訳文を作ると、
後工程で全部書き直しになります。**最初に聞くべきことのトップ 2** です。

**この 18 は練習用の作品 (リィンフォルト戦記) の数字です。** 僕の夏休み 2 の
枠の幅は**まだ分かっていません** —— 開発元の仕様書が手に入らないからです。
公開ソースで測れるものは 2 つあります。

* **日本語の原文** —— `test.txt` の会話の抜粋 71 行。いちばん長い行で **13.5 文字分**
* **Hilltop が同じ枠に収めた英訳** —— `diaries.txt` 825 行 / `sumo_script.txt` 182 行 /
  `bug_info.txt` 23 行。いちばん長い行で **13.0 文字分** (半角は 0.5 で数える)

どちらも 18 に遠く届きません。つまり **18 のままだと、原文も英訳も一度も
使っていない広さまで訳文を通してしまいます**。

**`data/font_chars.txt` (文字表) は、この 3 つのうちいちばん危ない**です。
練習用は **347 字**、僕の夏休み 2 は **1656 字**。公開ソースの会話を 20 行かけると
「フォントに無い文字」が **14 件** 出ますが、**全部まちがい**です。正しい原文を
直しにかかることになります。`proofread.py` は、練習用の文字表のまま落ちたときに
**「訳文ではなく文字表のせい」**と名指しします。docs/10 の手順 6 で作った
文字表を `--font-chars font.txt` で渡してください。

**`lines_max: 3` も同じで、しかも「枠は 1 種類ではない」という問題があります。**
Hilltop が実機に収めた**日記**は 111 ページで **5〜9 行**ありました。会話の枠と
日記の頁は別物なので、日記の文に `lines_max: 3` を当てると全ページが ERROR に
なり、**本物の誤りが偽の ERROR に埋もれます**。`proofread.py` は行数で大半が
落ちたときにそう言うので、`--lines-max` を枠ごとに変えて別々に見てください。`proofread.py` は原文の実測を毎回出すので、
上限と見比べてください。`--line-width 13` のように試すこともできます
(実物の枠の幅が分かったら、その数字に直す)。

あわせて確認しておくもの:

* フォントに入っている文字の一覧 (`data/font_chars.txt` に相当するもの)
* 使える制御コードとその意味
* 変数が実際に何文字まで伸びるか (プレイヤー名は何文字入力できるか)
* テキスト領域の容量に余裕があるか

## 用語集

`data/glossary.tsv` の形です。実務では開発元やパブリッシャから支給されます。

```
term	forbidden	note
リィンフォルト	リンフォルト|リィンフォルド	国名。「ィ」を落とさない
薬草	やくそう|クスリ草|薬そう	アイテム名。漢字表記で統一
```

`note` 列を軽く見ないことです。指摘を出したあと「なぜそれが誤りか」を
説明できないと、開発側との議論で通りません。実務で一番読まれる列です。

チェックは 2 方向でかけます。

* **誤表記が使われていないか** (ERROR)
* **原文にあった正式表記が訳文から消えていないか** (WARN) — 意訳で用語が
  落ちるのはよくあることで、意図的なら問題ありませんが確認は必要です

## 変数と文字数

差し込みタグは、実行時に何が入るかで行幅が変わります。既定では `<VAR:00>` を
幅 0 として数えるので、**そのままではプレイヤー名が入ったときの実際の行幅が
分かりません。**

```
<VAR:00>！　こんなところにいたのね。
```

プレイヤー名が 6 文字なら、この行は 14 文字ではなく 20 文字になります。
仕様上の上限 18 を超えます。

実務ではこれを次のように扱います。

* 変数の最大長を仕様として確認する (「名前は最大 6 文字」)
* チェックは最大長を入れた状態で行う
* 最悪ケースの名前を入れて実機で確認する (`ながいなまえ` などのテスト用データ)

`--var-width` で最大長を渡すと、その分を数えます。

```bash
python3 tools/proofread.py exercises/qa_target.tsv --var-width 6
```

既定は 0 (数えない) です。仕様として決まっているなら `data/rules.json` の
`var_width` に書いておくと、毎回打たなくて済みます。

**既定を 0 にしてあるのは、この題材の原文そのものが 0 を前提に書かれている
からです。** `--var-width 6` を付けると、原文の側にも 2 行の違反が出ます
(id 2 が 20 文字、id 22 が 19 文字)。これは仕込んだ不具合ではなく、
**名前の長さを考えずに書かれた文章**です。実際の案件でもこうなります。
だから「変数の最大長を仕様として確認する」が最初に来ます。

なお `tools/make_viewer.py` の画面ではプレイヤー名を打ち替えられるので、
何文字までなら収まるかをその場で確かめられます。

## 禁則処理

日本語の組版ルールです。ゲームは行の折り返しを `<BR>` で人間が決めるので、
校正者の責任範囲に入ります。

* **行頭禁則** — 行の先頭に来てはいけない文字: `。、）」』！？ー` 小書きかな
* **行末禁則** — 行の末尾に来てはいけない文字: `（「『`

`data/rules.json` の `forbid_line_start` / `forbid_line_end` で調整できます。
ゲームによっては「行頭の `……` は許容」のように運用が違うので、
厳密な JIS 準拠にこだわらず案件のルールに合わせます。

## レポートを出す

指摘は口頭ではなくファイルで渡します。

```bash
python3 tools/proofread.py exercises/qa_target.tsv --report work/qa_report.tsv
```

`id / severity / rule / message / detail` の TSV になります。実務では
これに「起票者・起票日・ステータス・開発側の回答」の列を足して
バグ票として運用します。

大事なのは **id (どのメッセージか) を必ず添えること** です。文章だけ書いて
「〇〇のセリフが」と伝えると、開発側が探せません。抽出した TSV の id、
できればファイル名とオフセットも添えます。

### 検査の一覧 (`rule` 列の名前と直し方)

指摘は **TSV に出てくる順** に並びます。表を上から順に直せば、行ったり来たり
しなくて済みます (同じ行に複数出たときは ERROR が先)。

レポートの `rule` 列に出る名前は次の 14 個。上から順に、**入れ直すと壊れるもの
(ERROR)** → **表示は通るが品質が落ちるもの (WARN)** です。

| `rule` | 重さ | 何を見ているか | 直し方 | 説明の節 |
| --- | --- | --- | --- | --- |
| `placeholder` | ERROR | `<NAME>` `<VAR>` などの差し込みが原文と訳文で一致するか (数・種類) | 落とした差し込みを戻す。増やしてもいけない | 変数と文字数 |
| `control` | WARN | `<WAIT:xx>` `<COLOR:xx>` `<VOICE>` などの制御タグが原文と一致するか。**`<BR>` `<CLEAR>` `<LT>` は見ません** (「機械で落とせるものは機械で落とす」の節) | `<WAIT>` の増減は意図を確かめる | 変数と文字数 |
| `line_width` | ERROR | 1 行の幅 (全角 1.0 / 半角 0.5) が `line_max_width` を超えていないか | 言い換えて詰める。`<BR>` を入れ直して行を分ける | 仕様は数字で受け取る |
| `line_count` | ERROR | 1 ページの行数が `lines_max` を超えていないか | ページを分ける (`<WAIT>` / クリア) か、文を削る | 仕様は数字で受け取る |
| `kinsoku` | WARN | 行頭に `。、」` など、行末に `「` などが来ていないか | `<BR>` の位置を 1 字ずらす | 禁則処理 |
| `halfwidth` | ERROR | 半角の英数記号、および**半角カナ**が混ざっていないか (どちらもフォントに無いことが多い。メッセージは別々に出る) | 全角に直す。仕様で半角可なら `allow_halfwidth` を true に | 機械で落とせるものは機械で落とす |
| `font` | ERROR | フォント画像に無い文字を使っていないか (`--font-chars`) | 別の字に言い換える、またはフォントに字を足す依頼を出す | 機械で落とせるものは機械で落とす |
| `glossary` | ERROR / WARN | 用語集の禁止語 (ERROR)、原文にある用語が訳文から落ちていないか (WARN) | 用語集の表記に揃える。落ちた用語を戻す | 用語集 |
| `notation` | ERROR / WARN | `ban_patterns` の表記ゆれ (例: 「ゲーム」「ゲイム」)。**カタカナに紛れた似た形の漢字**もここ (「コ一ヒ一」の `一` は長音 `ー` ではなく漢数字) | 設定の `message` のとおりに直す | 用語集 |
| `empty` | ERROR | 訳文に**タグしか残っていない** (`<WAIT>` だけ、など。本文だけが消えた) | 本文を戻す。欄ごと空なら `untranslated` のほう | 手作業に残る部分 |
| `untranslated` | WARN | **訳文の欄が空** (このままだと原文がそのまま実機に出る) | 訳を入れる | 手作業に残る部分 |
| `number` | ERROR | 本文に出てくる数が原文と訳文で一致するか (全角と半角は同じ数として見る) | 原文の数に戻す。原文のほうが誤っているなら開発元に確認する | 数字は字面では気づけない |
| `consistency` | WARN | 同じ原文が、別の行で別の訳になっていないか | どちらかに揃える。文脈で訳し分けが正しいこともあるので WARN | 数字は字面では気づけない |
| `room` | WARN / ERROR | 訳文が**原文の入れ物に入るか** (`size` の欄があるときだけ)。Shift-JIS の枠に cp932 で書けない字を入れたら ERROR | 短く言い換える。`size` が無い TSV では**この検査は動きません**と出る | 入れ物の大きさ |

`--no-font-check` を付けると `font` を飛ばせます (文字表がまだ無い段階で使う)。

## 数字は字面では気づけない

ここまでの検査は、どれも「訳文だけを見て」判断できるものでした。字数、禁則、
半角、フォント、用語。目を皿にすれば人でも拾えます。

拾えないものが 2 つあります。

**1 つ目は数字です。** 「報酬は８５０ギル」が「報酬は８５ギル」になっていても、
字数は減るだけ、用語は正しい、禁則にも触れない。**日本語としてどこも
おかしくありません。** 気づく方法は原文と見比べることだけで、それは人が
何百行もやると必ず取りこぼします。実機では「850 もらえる」と言われて 85 しか
入らない、という出荷事故になります。機械なら確実です。

**2 つ目は訳ぶれです。** 「いいえ」が別の場所で「いえ」になっている。1 行だけ
見れば何の問題もありません。**行をまたいで見て初めて**分かります。担当者や
作業日が分かれるほど起きやすく、選択肢やメニューのように何度も出る短い文ほど
危ない。これも機械の仕事です。

> 1 行ずつ見る検査で拾えるものと、**原文と照らす / 行をまたぐ**検査でしか
> 拾えないものは別物。後者を人の注意力に任せない。

`consistency` を WARN にしてあるのは、文脈によって訳し分けるのが正しい場合も
あるからです。ERROR にすると、正しい訳し分けを直させてしまいます。

## 形が同じで別の字 (実際に製品に残った例)

**2 つ目に人が拾えないのは、形が同じで別の字です。** 長音記号 `ー` (U+30FC) と
漢数字の `一` (U+4E00) は、小さいビットマップフォントでは**まったく同じに見えます**。
「コ一ヒ一牛乳」を画面で見て、間違いに気づける人はいません。

これは作り話ではありません。**僕の夏休み 2 の英語化パッチの公開ソースに、
取り出した日本語がそのまま残っています** (`MSG.py` の `MENU_TEXT_EXCEPTIONS` /
`BUGGED_LINES`)。買い物メニューの「コ一ヒ一牛乳」「ジェットサイダ一」
「ベ一スボ一ルバ一」、虫相撲の「グレ一ト」「ハリケ一ン」——**全部 `一` (漢数字)** です。
向こうの文字表には `ー` (番号 1589) と `一` (番号 279) が別々に入っているので、
どちらの字かは区別できています。

原因は 2 通り考えられて、**手元のデータだけではどちらとも決められません**。

| 見立て | もしそうなら |
| --- | --- |
| 製品のデータが本当に `一` を使っている | 発売された製品に残った誤字。QA が拾うべきだったもの |
| 文字表を作るときに 2 つを取り違えた | 取り出し側の誤り。docs/10 の「文字表の下書き」でいちばん起きやすい型 |

**どちらでも、教訓は同じです。** 形の似た字は目で確かめられないので、機械に見張らせる。
`notation` に検査を 1 つ入れてあります: **カタカナの並びの中に、形の似た漢字が
混ざっていたら WARN**。対象は `一 力 口 二 工 八 夕 卜 厶` (それぞれ
`ー カ ロ ニ エ ハ タ ト ム` と紛らわしい)。

**両隣がカタカナのときだけ**に絞ってあります。「コーヒー**一**杯」「カード**一**枚」は
正しい日本語なので、そこで鳴っては使い物になりません。上の実例 11 個で測ったところ、
**11 個とも拾って、正しい日本語 15 個では 1 つも鳴りません**でした。

## 半角の `?` を、訳文のせいにしない

`halfwidth` の ERROR がいちばん出やすい形が **半角の `?`** です。訳者が打った
とは限りません。**保存の仕方で勝手に増えます。**

Excel やメモ帳の「ANSI」(cp932) で保存すると、cp932 に無い字は**その瞬間に
`?` に変わります**。僕の夏休み 2 のフォント (1656 字) には cp932 で書けない字が
**4 つ**あり —— `¥` `—` `♡` `︙` —— `♡` は台詞に普通に出ます。

```text
保存前: ぼくの♡なつやすみ     ANSI で保存     ぼくの?なつやすみ
                              ───────────→
```

訳文をいくら直しても直りません。直すのは保存形式のほうです
(Excel は「CSV UTF-8」、メモ帳は「UTF-8」)。`proofread.py` は 2 通りで気づきます:

* TSV そのものが cp932 で保存されている
* 原文には cp932 で書けない字があるのに、訳文はその場が `?` になっている

どちらでも「**訳文の書き方の問題ではありません**」と言います。文字表
(`font.txt`) も同じで、そちらは `boku2.py check` / `text` が言います
(本物の `?` はフォントに 1 つだけなので、2 つ以上あれば潰れた疑い)。

## 入れ物の大きさ

幅や行数は**読みやすさ**の話です。入れ物の大きさは**物理**の話で、外すと
「訳したのに入らない」が実機に入れる段で初めて分かります。英語化パッチを出した
先行事例が、そのために文字列を詰める道具を別に書いているくらい、この作品では
効いてくる制約です。

`boku2.py text` が書き出す TSV には `size` の欄があり、**その文がディスク上で
占めていたバイト数**が入っています。`room` はそこを見ます。

```
WARN  room  訳文が 40 バイトで、原文の入れ物 12 バイトに 28 バイト入りません
```

数え方は 2 通りあります。

| どこ | 1 字 | 終わりの印 | 詰め物 |
| --- | --- | --- | --- |
| 本文 (`.msg` / マップの会話) | 2 バイトの文字番号 | `0x8000` (2 バイト) | 4 バイト境界まで `0xCDCD` |
| 保存画面の一部 | Shift-JIS (全角 2 / 半角 1) | 無し | 無し |

どちらの枠かは、**原文と `size` を突き合わせれば決まります** (両方に当てはまる
大きさは出てきません)。決まらない行では**何も言いません** ——
そのときは「N 行は入れ物の大きさが数えられませんでした」と、何行ぶん見ていないかが
出ます。`size` の欄が無い TSV (docs/01〜03 の練習用など) では、
「入るかどうかの検査は動いていません」と出ます。

**詰め物の分はおまけしています。** 元の文は 4 バイト境界まで詰めてあるので、
`size` は中身より 2 バイト大きいことがあります。入れ直すときに詰め直すかどうかは
入れる側の都合なので、ここでは**詰めない大きさ**で見ています。

Shift-JIS の枠に cp932 で書けない字 (`¥` `—` `♡` `︙`) を入れた場合だけは
ERROR です。大きさの問題ではなく、**その枠には書きようがない**からです。

## id は触らない

`id` は**入れ直す先の住所**です (`ファイル名:番号`)。取り出したままなら全部違います。

| 起きたこと | 道具の言い方 | なぜ困るか |
| --- | --- | --- |
| 行を複製した | 「同じ id の行が N 種あります」 | 入れ直す段で**どちらか片方が黙って消える** |
| id の欄を消した | 「id の欄が空の行が N 行あります」 | **どのセリフか分からない**ので入れ直せない |

**番号が飛んでいるのは事故ではありません。** `.msg` には中身の無い項目があり、
取り出しはそこを飛ばすので、`holes:0 / holes:2 / holes:4` は正しい姿です。
だから道具は「飛び」では鳴りません (鳴らせば健全なファイルで鳴ってしまう)。

`compare_tsv.py` は同じ重複を**断って止まります**。あちらは id で 2 つの TSV を
突き合わせる道具なので、重なっていたら仕事になりません。1 行ずつ見る
`proofread.py` は、言ってから先へ進みます。**同じ事故でも、道具によって
扱いが違ってよい** —— 理由が違うからです。

## 1 行ずれ (表計算でいちばん高くつく事故)

取り出した TSV は `translation` が `original` の写しです。表計算で行を 1 つ
挿入・削除したまま訳し始めると、そこから下の訳文が**全部、隣の行のもの**になります。

**1 行ずつ見ても分かりません。** 原文と訳文が違うのは訳したのだから当たり前で、
`placeholder` も `number` も `room` も鳴りません。気づくのは実機に入れてから、
しかも直すには全行を突き合わせ直すことになります。

そこで `proofread.py` は**行をまたいで**数えます。「訳文が、すぐ上 (または下) の
行の原文と同じ」がたくさんあれば、ずれを疑って言います。

```
注意: **訳文が 1 行ずれている疑い**があります。30 行で、訳文が**すぐ上の行の原文**と
同じです (最初の例: diary#0:1)。
```

`id` の欄は取り出したときのままなので、**id を頼りに取り出した TSV と並べれば**
どこからずれたかが分かります。並べ替えや行の挿入をしたら、**id が続き番号か**を
必ず確かめてください。

少数の一致では鳴りません (「はい」「いいえ」のような定型文は、隣と同じになることが
あるため)。数と割合の両方で見ています。

## 動いていない検査に気づく

この一覧のうち **`placeholder` `control` `number` `empty` `untranslated` の 5 つは、
原文と訳文を見比べて**初めて意味を持ちます。取り出したばかりのテキストは訳文の欄が
原文のままなので、この 5 つは**何も見ていません**。

```
23 行をチェック: ERROR 0 件 / WARN 0 件 / 問題なし 23 行

注意: 23 行すべて訳文の欄が原文と同じです。原文と見比べる検査は動いていません:
  placeholder / control / number / empty / untranslated
```

「問題なし 23 行」だけを見ると、13 個の検査を全部通ったように読めます。実際には
8 個しか働いていません。**緑は「問題が無い」ではなく「見つけられなかった」**
としか言っていない、という話がここにも出てきます。

**「訳文が原文と同じ」は行ごとの指摘にしていません。** 取り出した直後は
全行がそうなので、行ごとに出すと同じ WARN が何十件も並んで、本当の指摘が埋もれます。
代わりに、上の**注意書き 1 つ**にまとめてあります。行ごとに出る `untranslated` は
これとは別で、**訳文の欄が空** (原文がそのまま実機に出てしまう) のときに出ます。

だから取り出し直後にこれをかける意味は、「訳文だけを見て分かる不具合」
(枠からはみ出す、フォントに無い字、禁則) を**原文の側で**先に潰すことにあります。
訳す前に原文が仕様違反なら、訳文も必ず違反します。

## 手作業に残る部分

機械が拾えないのはこのあたりです。人間の目を使う場所です。

* **口調と人物の一致** — `data/names.tsv` の役割メモと突き合わせる。
  ガルド (老兵、「わし」) のセリフがくだけた口調になっていないか
* **文脈** — 選択肢の「はい/いいえ」が、直前の問いに対して自然か
* **同じ文の使い回し** — ポインタを共有している文を片方だけ直そうとしていないか
  ([03-ポインタテーブル.md](03-ポインタテーブル.md))
* **画面で見たときの読みやすさ** — 幅も行数も仕様内なのに詰まって見える、など

最後の項目のために、実務では必ず実機・実ビルドで表示を確認します。
データ上の文字列と画面のセリフを照合する作業が、結局いちばん確実です。
このリポジトリではその工程を `tools/make_viewer.py` で再現できます
→ [06-画面で確かめる.md](06-画面で確かめる.md)
