# ポインタテーブル — 各セリフの開始位置

セリフは長さがまちまちなので、ゲームは「何番目のセリフがどこから始まるか」の
一覧を別に持っています。これが **ポインタテーブル** です。
テキストを入れ直すときに必ず触ることになる部分で、ROM ハックでいちばん多い
失敗もここです。

## 構造を見る

```bash
python3 tools/hexdump.py work/MSG_ENC.BIN --struct
```

```
work/MSG_ENC.BIN  1,448 バイト

  0x00  マジック      'SCRP'
  0x04  version       1
  0x08  count         39
  0x0C  encoding      1 (custom)
  0x10  ポインタテーブル (39 x 4 = 156 バイト)

   id   ポインタ   生バイト (LE)    本文サイズ
    0   0x000AC   AC 00 00 00        39 バイト
    1   0x000D3   D3 00 00 00        58 バイト
    2   0x0010D   0D 01 00 00        32 バイト
```

要点が 3 つあります。

### 1. リトルエンディアン

`0C 01 00 00` は `0x0000010C` = 268 です。低い桁が先に来ます。
PS2 の CPU (MIPS R5900) がリトルエンディアンなので、実機のデータは
基本これです。16 進を見て「逆から読む」のに慣れるのが第一歩です。

慣れないうちは電卓を使わず、次のように口で言えるようにします。

```
2C 01 00 00  →  01 2C  →  0x12C  →  300
```

### 2. ポインタの基準がどこか

このフォーマットは「ファイル先頭からの絶対オフセット」ですが、実際のゲームは
いろいろです。

| 方式 | 例 | 見分け方 |
| --- | --- | --- |
| ファイル先頭から | このフォーマット | 先頭のポインタ = テーブル直後の値になる |
| テキスト領域の先頭から | ポインタ値が小さい | 先頭のポインタが `0` か小さい値 |
| メモリ上のアドレス | `0x001C_8A40` など巨大 | 全ポインタから一定値を引くと file 内に収まる |

判定の定石は **「先頭のポインタ値」と「本文が始まっている位置」を引き算する**
ことです。差が一定なら、それが基準値 (ベースアドレス) です。

### 3. 隣のポインタとの差 = 本文の長さ

`0x0D3 - 0x0AC = 0x27 = 39` バイト。id 1 なら `0x10D - 0x0D3 = 0x3A = 58` バイト。
終端バイト (`0xFF`) を探さなくても、
隣のポインタとの差で長さが分かります。逆に、この性質を使って
「ポインタ表が本当にポインタ表なのか」を検証できます。値が単調増加していて、
差が数十バイト程度なら、まずポインタ表です。

## 同じ場所を指すポインタ

「はい」「いいえ」のように同じ文が何度も出てくる場合、本文を 1 か所に置いて
複数のポインタから共有することがあります。容量節約の定番です。

```bash
python3 tools/make_sample.py --pool-duplicates
python3 tools/hexdump.py work/MSG_ENC.BIN --struct | grep 同じ
```

```
   37   0x00165   65 01 00 00         3 バイト  ← id 4 と同じ場所
   38   0x00168   68 01 00 00         4 バイト  ← id 5 と同じ場所
```

**校正のときに注意が必要なのはここです。** 共有されている文を 1 か所だけ
直したつもりでも、全部の出現箇所が変わります。逆に「片方だけ表現を変えたい」
と言われたら、データの作りから変える必要があるので開発側に相談する話に
なります。抽出した TSV でポインタが重複している行は、この可能性があります。

## 入れ直すときにやること

`tools/insert_text.py` がやっているのは 2 つだけです。

1. 各メッセージを文字コードに戻して `0xFF` 終端のブロックにする
2. 全ブロックを並べ直し、先頭オフセットからポインタテーブルを作り直す

```bash
python3 tools/insert_text.py work/SCRIPT.tsv -o work/SCRIPT_new.BIN \
    --original work/SCRIPT.BIN
```

何も編集していなければ、出力は元のファイルとバイト単位で一致します。

```bash
cmp work/SCRIPT.BIN work/SCRIPT_new.BIN && echo 一致
```

**長さを変えたのにポインタを直さないと何が起きるか** を確かめておくと、
この工程の意味が身体で分かります。ゲーム側は古いオフセットを読み続けるので、
セリフが途中から始まったり、終端を読み飛ばして次のセリフまで繋がったり、
文字化けしたりします。

## 容量の制約

実際のディスクイメージではファイルの前後に別のデータが詰まっているので、
テキストファイルを勝手に大きくできません。`--original` を付けると
元のサイズを上限として扱います。

```bash
python3 tools/insert_text.py exercises/qa_target.tsv -o work/BAD.BIN \
    --original work/SCRIPT.BIN
```

```
エラー: 2,128 バイトで、上限 2,120 バイトを 8 バイト超えています。
       文章を詰めるか、--pool-duplicates か --allow-grow を検討してください。
```

超えたときの打ち手は、実務でもこの順です。

1. **文章を詰める** — 校正側の仕事。まずこれ
2. **重複をまとめる** (`--pool-duplicates`) — 同一文があるなら効く
3. **領域を広げてもらう** — 開発側の作業になるので交渉が必要

日本語から英語へのローカライズでは、同じ内容でも文字数が 1.5〜2 倍に
膨らむので、この「入らない」問題が案件の主要な論点になります。
逆に英語から日本語なら縮むことが多く、余った領域をどう扱うかの話になります。
