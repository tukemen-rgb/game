# 実物のディスクを扱う場合

このリポジトリの練習には実物のソフトは必要ありません。それでも
「実機のデータはどう手に入れるのか」を知っておくと全体像が繋がるので、
技術的な流れと、その前に確認すべきことを整理しておきます。

## 技術的な流れ

PS2 のディスクは標準の DVD-ROM / CD-ROM です。**専用の読み取り機は不要で、
普通の PC 用 DVD ドライブ (内蔵・USB 外付けどちらでも) で読めます。**

1. **イメージ化** — ImgBurn の Read モードなどでディスク全体を `.iso` にする。
   以降は原本に触らず複製データだけで作業する
2. **中身を見る** — 7-Zip で展開するか、Windows 標準の機能で `.iso` をマウントする
3. **ファイルを絞る** — テキストが入っていそうなファイルを探す。
   `.BIN` `.DAT` `.PAK` `.AFS` のような拡張子や、サイズの大きいアーカイブが候補
4. **文字コードを見る** — バイナリエディタ (HxD) で開き、Shift-JIS の日本語が
   そのまま見えるか確認する → [01-文字テーブル.md](01-文字テーブル.md)
5. **独自コードなら相対検索** — Monkey-Moore で位置とテーブルを割る
   → [02-相対検索.md](02-相対検索.md)
6. **フォントが画像なら** — Crystal Tile 2 でグリフの並びから文字テーブルを作る
7. **画面と照合する** — PCSX2 (PS2 エミュレータ) で `.iso` を起動し、
   「画面のセリフ」と「データ上の文字列」を突き合わせる

7 番が一番効率的な学び方です。データ上のどのバイト列が画面のどのセリフに
なるのかを目で確認できるので、推測が確信に変わります。

なお 3 番の「ファイルを絞る」が実は一番手間のかかる工程です。ひとつの
巨大なアーカイブに全部詰まっていて、その中身の構造から解析しないと
テキストに到達できないことも珍しくありません。このリポジトリの
`work/SCRIPT.BIN` のように素直に置いてあるのは、練習用だからです。

## 実物のディスクを探査台で開くときの手順

`web/` の構造探査台は、練習用データだけでなく実物のイメージでも動きます。
PS2 の市販ディスクを想定した進め方を書いておきます。

### 1. まずファイル一覧と色の帯を見る

`.iso` をドロップすれば ISO9660 のファイル一覧が出ます。**すでに吸い出して
展開済みなら、「フォルダごと読む」でフォルダをまるごと渡せます** (複数ファイルの
ドロップでも同じです)。左の一覧には各ファイルの先頭 4KB を分類した色が付くので、
**開く前に当たりが付きます。**

| 色 | 中身の見当 | 次にやること |
| --- | --- | --- |
| 緑 (ASCII) | 設定ファイル、スクリプトのソース | そのまま読む |
| 水 (日本語) | Shift-JIS のテキスト | 文字列タブで読める |
| 藍 (タイル・コード) | 画像、フォント、実行コード、独自コードのテキスト | 見つけた絵 / 相対検索 |
| 桃 (高エントロピー) | 圧縮、動画 | ここで止まる (下記) |
| 橙 (波形) | 音声 | 対象外 |

### 2. SYSTEM.CNF を見る

ルートにある小さな ASCII のファイルです。`BOOT2 = cdrom0:\SLPS_xxx.xx;1` の形で
起動プログラムの名前が書いてあり、これがそのタイトル固有の型番になります。
指している ELF が本体プログラムです (先頭 4 バイトが `7F 45 4C 46`)。

### 3a. 索引ファイル + データ本体の組

**市販タイトルでいちばん多い形です。** 吸い出したフォルダに

```
BOKU2.IDX      56 KB      索引
BOKU2.IMG     453 MB      データ本体
BOKU2.CRC     100 KB      検査用の値らしきもの
```

のような対があったら、これです。小さい方が索引で、大きい方に中身が入っています。

「索引ファイル」タブで両方を選んで**「解析する」**を押すと、レコード長・位置の列・
長さの列・単位を総当たりして候補を出します。見ているのは 3 点です。

1. 位置が減らずに増えるか
2. 本体の大きさをはみ出さないか
3. 本体をだいたい使い切っているか (被覆率)

**単位が肝です。** PS2 のアーカイブは位置を**セクタ (2048 バイト) 単位**で持って
いることが多く、バイト単位だと思って読むとまったく違う場所を指します。
バイトとセクタの両方を試すようにしてあります。

候補を選ぶと、**その解釈で実際に本体を読んで先頭 24 件の中身を見せます。**
`SCRP` のような目印が並んだり、種類が「日本語テキスト」「タイル」と出れば、
その解釈で合っています。そのまま「切り分ける」を押せば、一覧に個別のファイルとして
並びます。

`練習したい場合は python3 tools/make_archive.py` で同じ形の
`work/PACK.IDX` と `work/PACK.IMG` が作れます (答えは実行時に表示されます)。

#### 索引の件数を別の方法で確かめる

`.CRC` のような、1 エントリにつき固定長の値が並んでいそうなファイルが一緒に
あるときは、**そのファイルサイズを候補の件数で割ってみてください。** 4 や 8 で
割り切れれば、その件数が正しい可能性が高いです。索引の解釈が合っているかを
別の角度から検算できます。

### 3b. 同じファイルの中に索引がある場合

索引が本体と同じファイルの先頭にある形もあります。その場合は
「ポインタ表」タブで先頭付近の表を選び、**「この表で N 個に切り分ける」**
を押すと、その索引に従って中身が個別のファイルとして一覧に並びます。
切り分けた断片をさらに選んで、同じことを繰り返せます (入れ子のアーカイブ)。

これが実物のデータを扱うときの主戦場です。索引の形は
「件数 + オフセットの並び」「オフセットと長さの対」「先頭が 0 の相対値」など
まちまちですが、基準の値を総当たりして根拠で選ぶ作りにしてあるので、
たいていの形は拾えます。

### 4. 署名で全体の地図を作る

「既知の形式」タブの**「ファイル全体を走査する」**は、数 GB のイメージでも
少しずつ読みながら走査します。確実に分かっている目印だけを探します。

| 目印 | 形式 |
| --- | --- |
| `7F 45 4C 46` | ELF 実行ファイル |
| `TIM2` | PS2 でいちばん普通のテクスチャ形式 |
| `VAGp` | Sony の ADPCM 波形 |
| `00 00 01 BA` | MPEG プログラムストリーム (動画) |

**ゲーム独自の形式は当然この一覧に入っていません。** 16 進や文字列を自分で
入れて探せるようにしてあるので、当たりを付けたらそこに入れてください。
文字列は Shift-JIS と UTF-8 の両方で探します。ゲーム内で見た固有名詞
(地名・人物名・アイテム名) を入れるのが、テキスト領域を見つける近道です。

### 5. 大きさの制限

詳しい解析 (文字列・ポインタ表・絵の検出) は、選んだファイルの先頭 24MB までです。
イメージの中の個別ファイルはたいていこれに収まるので実用上は問題になりません。
イメージ全体を選んだときは、地図と署名の全体走査だけが全域を見ます。

## ここで止まる壁

正直に書いておきます。**圧縮されていたら、この道具では中身に届きません。**

PS2 世代のゲームは LZSS 系の独自圧縮を使っていることが多く、伸張ルーチンは
本体プログラム (ELF) の中にあります。展開するには、そのルーチンを逆アセンブル
して読み解くか、同等の実装を書く必要があります。

実際のところ、**そこまで行くなら PCSX2 でゲームを動かして、メモリ上の展開後の
データを見るほうが早い**ことが多いです。エミュレータのメモリダンプを取り、
それを探査台に読み込ませれば、展開済みのテキストや画像がそのまま見つかります。
「ディスクから読む」より「メモリから読む」ほうが近道になる、というのは
この分野ではよくある逆転です。

## 安全面

**技術面** — 上に挙げたツールはどれも定番で、正しく使えば PC もディスクも
壊しません。読み取りは読み取り専用の操作です。ただしソフトは公式・信頼できる
配布元から入手してください。ツール名で検索すると偽の配布サイトが上位に
出てくることがあります。

**法律面** — ここは技術の話とは別に、はっきり認識しておく必要があります。

* 日本の著作権法では、自分が持っているソフトであっても
  **コピーガード (技術的保護手段) を回避したコピーは、私的目的でも違法に
  なり得ます。** PS2 ソフトはこれに該当する場合があります。
* 取り出したデータの配布、改変したものの公開は、明確に問題になります。
* 最終的な法的判断は、この文書ではなく専門家に確認してください。

つまり「技術的にできる」と「やってよい」は別問題です。

## 権利面がクリアな題材で同じ練習をする

重要なのは、**ローカライズ・校正の技術そのものは、権利的に問題のない題材で
まったく同じように練習できる** ということです。このリポジトリがその一例です。

ほかの選択肢:

| 題材 | 良い点 | 注意点 |
| --- | --- | --- |
| このリポジトリの疑似データ | 答えがある。構造を自分で変えられる | 実データ特有の癖はない |
| 自作のテストデータ | 好きな構造を試せる | 自分で作る手間 |
| フリーの同人ゲーム | 実データの手触りがある | 改変・再配布の許諾条件を必ず確認する |
| オープンソースのゲーム | 権利関係が明確 | テキストが素のままで解析の練習にならないことも |
| 練習用に公開されている ROM ハック素材 | 教材として整備されている | 素材自体の出所を確認する |

## 実務ではどうなるか

将来ローカライズ QA・校正の仕事を目指す場合、**吸い出しの技術を使う場面は
ほぼありません。** 開発元から正規のテキストデータ (Excel、XLIFF、専用ツール
上のデータなど) を受け取るのが普通です。

代わりに毎日効くのは、このリポジトリで扱っている中身の理解です。

* 文字コードとフォントの仕組み → 文字化け・□ の切り分けができる
* 表示幅と行数の制約 → 訳文を作る時点で入る形にできる
* ポインタと容量の制約 → 「入りません」と言われる理由が分かる
* 変数と制御コード → 壊してはいけないものが分かる

だから練習の重点は「吸い出せるようになること」ではなく
「取り出したあとに何を見るか」に置くのが正解です。
