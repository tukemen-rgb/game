# 形式を突き止めるまで — 僕の夏休み 2 で実際に辿った道

手順書 (docs/10) は「分かった後」の順路です。この文書は「分かるまで」に何を
見て、どこで間違え、何が決め手になったかの記録です。次に別の作品を扱うとき、
同じ回り道をしないための教材として残します。

## 1. 入口は本体プログラムだった

吸い出したフォルダには `SYSTEM.CNF`、本体 `SCPS_150.26`、`BOKU2.IDX` / `BOKU2.IMG`、
`MAP/` などがありました。最初に効いたのは **本体プログラムの逆アセンブル**です。

- `SYSTEM.CNF` が指す `SCPS_150.26` は ELF32 / MIPS R5900。
- 「文字列を使っている場所を全部探す」で、開発時のパス (`/project6/boku2/cdimg/…`) と
  `system.msg` `namemsg.msg` `bk_font.tms` のような **ファイル名が本体に埋まっている**
  ことが分かった。→ 探すべき名前が確定した。
- 0x001293D8 の関数が「先頭が `DFI` ならバッファ + 0x10 を一覧の先頭にする」と
  書いていた。→ `BOKU2.IDX` の先頭 16 バイトがヘッダで、レコードが 16 バイトずつ
  続くことの **根拠**になった。

学び: ファイル名は最初に本体から拾う。索引の形はコードが教えてくれる。

## 2. 索引は読めた。名前だけ読めなかった

レコードの `+8` (セクタ) と `+12` (長さ) は正しく、本体を 1951 個に切り分けられた。
先頭の塊が全部 `TIM2` (日記の写真) で、位置と長さが合っている証拠になった。

ところが名前が出ない。`+4` の値を「名前の位置」と決めつけ、6 回直しても
実データで外れ続けた (走りの中で値が減っていく、名前の置き場は 0x8142 から始まる、
などの観察はあったのに、**仮説を捨てられなかった**)。

学び: 同じ仮説で 3 回外れたら、仮説そのものを疑う。観察 (名前が 0x8142 から
順に並んでいる) のほうが仮説より正しい。

## 3. 「圧縮」という思い込み

生の `BOKU2.IMG` を日本語で検索しても何も出ない。報道記事に「翻訳者が独自の
圧縮を書く必要があった」とあり、これを **テキストが圧縮されている**と読んだ。
LZSS の道具まで作った。

実際は違った。記事の「圧縮」は、英訳を元の容量に収めるための **文字列の
詰め込み** のこと。テキストは圧縮されておらず、**フォント画像の並び順を
そのまま文字コードにした 2 バイトの並び**だった。Shift-JIS で検索しても出ないのは
当然で、docs/01 の「文字テーブル」の実物そのものだった。

学び: 二次情報 (記事) の言葉を、一次情報 (データやソース) で確かめる前に
設計の前提にしない。「検索して出ない」は「圧縮」ではなく「文字コードが違う」の
可能性を先に疑う (docs/02 の相対検索が、まさにそのための道具)。

## 4. 決め手は先行事例のソースだった

行き詰まりの規則どおり外部を当たり直したら、翻訳パッチのツールのソースが
公開されていた。読んで確定したこと:

| 分かったこと | どこで |
| --- | --- |
| 索引の名前はレコードの直後にレコード順で並ぶ。`+4` は使われていない | `UNPACK.py` |
| `+2` は「同じフォルダにまだ続くか」。フォルダの入れ子はこれで復元 | `UNPACK.py` |
| `.msg` は「件数 + 位置表 + 2 バイトの本文」。0x8000 終わり / 0x8001 改行 / 0x8002 待ち | `MSG.py` |
| マップの入れ物は「項目数 + (位置, 長さ)」、1 番が会話 (表が複数) | `MSG.py` |
| フォントは 1 行 23 字、文字の刻み 0x16 = 22 ドット (描く枠は 0x17 = 23 で 1 ドット重なる) | `reprint.py` の `N_COLUMNS = 23` / `CELL_WIDTH = 22`、`asm_notes.txt` の `(char%0x17)*0x16` と `+0x17` (同じ文書の「char%17」は 0x17 の書き落とし。数字 1 つでも出典を 2 つ以上で突き合わせる) |

読んだのは **形式** だけで、向こうのデータや訳文は取り込んでいません。形式を学び、
読み取りは自分で書き直し、合成データで両方向から検証しました (docs/09 #4〜#9)。

学び: 「先行事例がある」と分かったら、記事ではなく **ソースを探す**。公開されて
いれば、それが最も速い一次情報になる。

## 5. 検証の組み立て

実物は手元 (社長の PC) にしか無いので、検証は次の 3 段で組みました。

1. **合成データ** — 公開ソースの規則どおりに架空データを組み立て (`make_boku2_sample.py`)、
   読み取りが答えと一致することを確かめる。
2. **二重実装の突き合わせ** — ブラウザ (JavaScript) と一括処理 (Python) が
   同じ合成データで同じ答えを出すことを確かめる。
3. **画面の操作** — ヘッドレスブラウザで docs/10 の手順をそのまま通す (`tests/e2e/`)。

実物で 1 つでも外れたら、外れた箇所 (先頭 16 バイトなど) を手がかりに、
合成データ側を実物に寄せて直す、という順番です。

## 6. 時間の使い方の反省

- 道具を増やすことと、目的に近づくことは別。#1〜#3 は道具が増えただけで
  テキストには近づいていなかった。
- 「実データが無いのに当てずっぽうで作る」時間が最も無駄だった。検証できない
  ことは、検証できる形 (合成データ・公開ソース) に置き換えてから手を付ける。
- 30 分に 1 回の「前進しているか」の点検が、方向転換のきっかけになった。

## 7. 形式が分かった後に踏んだこと (#17〜#26)

形式が確定してからも、細かい所で 4 回踏みました。どれも「合成データで検証して
いたから気づけた」ものです。

| 踏んだこと | 何が起きたか | 直し方と学び |
| --- | --- | --- |
| 練習データの旗を 1 つ間違えた (#17) | フォルダの「まだ続くか」を 1 か所誤り、最後のファイルが根に戻らなかった | 読み取り側は正しく、データ側の誤り。**データを作る側にもテストが要る** (答え合わせを機械で) |
| 同じ道筋が黙って上書きされる危険 (#18) | 入れ子の規則は推定なので、実物で外れると別フォルダの同名ファイルが衝突する | 上書きせず `~2` を付け、件数を画面に出す。**推定した規則には、外れたときの合図を付ける** |
| 索引の名前をそのままフォルダ名に (#22) | `..` や `\` が入っていれば出力先の外に書く | 索引は入力。**入力は信用しない** |
| 入れ物の刻み (8 / 12 バイト) の誤認 (#24) | 12 バイト刻みの入れ物は、後ろの項目が空だと 8 バイト刻みとしても「読めて」しまう | 両方試して **部品が多く取れる方** を採る。「最初に通った解釈」で止めない |
| 公開が弾かれた (#25) | ソースに生の置換文字 (U+FFFD) を書いた | エスケープで書き、組み立て時のテストで見張る。**同じ失敗は 2 度踏まない** |

まとめると、形式の解読は「規則を推定する」作業で、推定には必ず外れ方があります。
外れたときに **黙って壊れる** か **合図を出す** かが、道具の良し悪しを決めます。

## 8. 公開ソースを二度読みして直した 7 点 (#49〜#57)

第 4 節で「公開ソースを読んで形式を学んだ」と書きました。ところが道具が一通り
できてから、同じソースを **数字 1 つずつ** 突き合わせ直すと、7 か所も違っていました。
一度読んで分かったつもりになっていた、ということです。

| 何が | 出典 (どのファイルの何) | こちらの何が違ったか | 教訓 |
| --- | --- | --- | --- |
| 7 つのメニューでは 0x8002 に引数が無い (#49) | `MSG.py` の `ALT_NEWLINE_FILES` と `alt_mode` | 常に「0x8002 + u16」で読み、次の字を飛ばしていた | **例外の一覧** はソースの定数に隠れている。定数の名前を全部読む |
| 表の一覧の位置は int (#49) | `MSG_notes.txt` | u16 + 詰め物と読んでいた | 記法のメモ (notes) と実装の両方を見る |
| 位置の読み方が出典の中で割れている (#55) | `MSG_notes.txt` は int、`unpackMapMSG` は short | 片方だけを信じた | **出典どうしが割れたら、両方で読める作りにする** |
| 文字の刻みは 22 ドット、枠は 23 (#51) | `asm_notes.txt` の `*0x16` と `+0x17` | 「1 字 23」と覚え、目盛りが 1 列に 1 ドットずれた | 数字が 2 つ並んでいたら、**どちらが何の数字か** を確かめる |
| 1 行は 23 字 (#52) | `reprint.py` の `N_COLUMNS = 23`、`FontRecognizer.java`、`font.txt` の行幅 | `asm_notes` の「char%17」を十進と読んだ (0x17 の書き落とし) | **数字 1 つでも出典を 2 つ以上で突き合わせる** |
| 入れ物の中に入れ物がある (#53) | `UNPACK.py` の `IMG_MAP_FILES` の `~fish_on_mem/11.bin` など | 1 段しか開けず、魚の説明が丸ごと抜けた | ファイル一覧の **パスの深さ** をそのまま読む |
| フォルダの閉じ方の規則が違い得る (#56) | `UNPACK.py` の `unpackIMG` (旗で 1〜2 段) | 「閉じたフォルダの続くが 0 なら親も (何段でも)」と一般化していた | 実物でしか決まらないことは、**決める材料を診断に出す** (両規則で突き合わせ) |

この 7 点の共通項は「読んだときに分かった気になった数字や規則を、動く道具ができて
から **もう一度、出典の行番号まで** 追い直した」ことです。二度目の読みは一度目より
ずっと速く、しかも一度目より多く見つかります。道具が一通り動いたときが、
出典を読み直す最良のタイミングです。

## 9. 道具を育てる側で踏んだこと (#38〜#65 の自走から)

形式の話ではなく、道具と文書を毎時間 1 つずつ増やしていく **進め方** で踏んだことです。
どれも「気をつける」では防げず、仕組みで防ぐしかなかったものです。

| 踏んだこと | 何が起きたか | 仕組みでの防ぎ方 |
| --- | --- | --- |
| 落ちているテストのまま押した (#56) | `python3 tests/run_tests.py \| tail -3` の終了コードは `tail` のもの。赤でも次のコマンドに進んだ | 終了コードを変数に取る (`rc=$?`) → `rc=0` のときだけコミット。パイプの後ろで判定しない |
| テストが黙って 1 つ減った (#63) | 新しいテストを既存の `def` 行の直前に挿し、その `def` 行を巻き込んだ。古いテストの本文が新しいテストの中に入り、件数は変わらず見えた | 変更のあとに **テスト名の一覧** (`-v` 相当) を出して数える。件数だけでは分からない |
| 公開だけが何時間も止まった (#42, #47, #52, #55) | コミットは同じ手で出したのに、公開 (再取得 → publish → 送付) を次の手に回した所で止まった | 「テストが通った直後の手」に公開と送付を入れる。次の手に回す物を作らない |
| 練習データが自分の思い込みを写していた (#56) | 4 段のフォルダを 1 つのファイルで閉じる形は、公開ソースの規則では表せない。自分の規則に合わせて練習データを作っていた | 練習データは **2 つ以上の独立した読み方で同じ答えになる形** にする。1 つの規則に合わせて作らない |
| 説明書が画面に追いつかない (#61, #63, #65) | 画面や道具に増えた物 (要約の行、目盛りの色、→ の種類、rule 名) が文書に無いまま数回進んだ | 画面・道具の文言を文書と機械で突き合わせる検査を置く。増やしたら検査が落ちて気づく |

まとめると、毎時間 1 つ進めるやり方で怖いのは「進んだつもりで止まっている」ことでした。
止まり方は毎回違って見えますが、共通するのは **確かめる手順が人の注意に依存していた**
ことです。注意ではなく、終了コード・一覧・検査という形に置き換えるたびに、同じ止まり方は
起きなくなりました。

## 10. 点数は当たり外れの目安にならなかった (#69)

フォント画像のマスの形と、同じ大きさで描いた候補の字の形を突き合わせて、文字表の
下書きを作る道具を入れました (#69)。作ったあと、**その点数が信用できるか**を測って
みたところ、素朴な思い込みが外れました。

ブラウザで 57 字を描いて当てさせた実測です。

| 測ったもの | 値 |
| --- | --- |
| 当たった字 | 46 / 57 |
| 合っている字の点数 (中央) | 0.776 |
| 間違えた字の点数 (中央) | 0.776 |
| 間違えた字の点数 (最大) | 0.806 |
| 合っている字の点数 (最小) | 0.664 |

**合っている字と間違えた字で、点数の分布がほぼ完全に重なっていました。** しきい値を
0.55 から 0.75 に上げると、間違いは 10 件から 9 件にしか減らないのに、当たりは 46 件から
31 件に落ちます。つまり「点数が低い所を人が見直す」というやり方は効きません。

効いたのは **1 番目と 2 番目の候補の点数の差** でした。

| 測ったもの | 値 |
| --- | --- |
| 合っている字の差 (中央) | 0.075 |
| 間違えた字の差 (中央) | 0.026 |
| 差の小さい順に 12 マス見たとき、拾える間違い | 6 / 11 |

差が小さいマスは「2 つの候補で迷った」マスなので、実際に間違いが集まります。画面が
「まず疑う所」として出しているのは、点数の低い順ではなく **差の小さい順** です。

間違え方にも偏りがありました。小書きの字と大きい字 (つ と っ、イ と ィ)、濁点の有無
(ケ と ゲ)、数字と英字 (0 と O、1 と I)、句点と半濁点 (。と ゜)。どれも**形が近い組**で、
書体が違えば当然こうなります。一覧にして文書に載せてあります。

学びとしては、**似ぐあいの点数を確からしさとして扱ってはいけない**、ということでした。
点数は「どれだけ重なったか」であって「合っている見込み」ではありません。確からしさが
欲しいなら、1 位の点数ではなく **1 位と 2 位の隔たり**を見ます。しかもそれは、思いつきで
決めずに測って初めて分かりました。道具を足したらその道具の精度も測る、という一手が
要ります。

### 形で足りない分は、並びが埋めた (#70)

間違いが「形の近い組」に偏っているということは、**形だけを見ているのが限界**という
ことでした。フォントは五十音順に並ぶのが普通なので、続いたマスが続いた字に当たって
いれば、その区間はまとめて並びで埋め直せます。支持したマスが 4 つ未満、または区間の
半分に満たなければ何もしません。並びが違うフォントでは支持が集まらないので、
**規則が自分で自分を止めます**。

これを入れて、同じ 57 字で測り直しました。

| | 当たった字 |
| --- | --- |
| 形だけ (#69) | 46 / 57 |
| 並び順で直したあと (#70) | 53 / 57 |

ここでもう一度、素朴な思い込みが外れました。**区間を外へ伸ばす**ときの条件です。
最初は「並びが言う字のほうが、いま付いている字より画像に似ていること」を条件に
しました。ところが、いま付いている字は形で選んだ勝者なので、この条件は**原理的に
ほぼ通りません**。区間は 1 マスも伸びませんでした。

そこで比で見ました。

| 伸ばした先 | 正しかったか | 並びが言う字 / いまの字 の比 |
| --- | --- | --- |
| ケ (ゲ になっていた) | 正しい | 0.95 |
| コ (ヨ になっていた) | 正しい | 0.99 |
| 。(゜ になっていた) | 正しい | 0.92 |
| サ (数字の 0 のマス) | 壊す | 0.33 |
| ス (数字の 2 のマス) | 壊す | 0.61 |

0.85 を境にすると、正しい伸ばしを通して、仮名の並びが数字のマスへ食い込むのを
止められました。**比較の向きを変えただけ**で使える条件になった、という一例です。

もう一つ、この回で踏んだ細かい失敗も書いておきます。区間を外へ伸ばす繰り返しで、
伸ばした端を更新しながら `端 + k` を見ていたため、**1 マスおきに飛ばして**いました。
テストの正解率が 52 で止まり、内訳を見て初めて気づきました。総数だけ見ていたら
「そういうものか」で通っていたはずで、**間違えた中身を並べて出す**ようにしていたのが
効きました。

## 11. 書き戻す側のコードに、形式の答えが書いてある (#71)

`.msg` の位置表には 2 つの形があって、片方は 1 項目 4 バイト (位置だけ)、もう片方は
1 項目 8 バイトです。後ろの 4 バイトが何なのかは分からないまま、「読むには要らない」と
書いて 50 回以上そのままにしていました。

分かってみれば簡単で、**その項目のバイト長**でした。見つけ方に学びがあります。

公開ソースの**読み取り側**は、位置しか使っていません。項目の終わりは「次の項目の位置」
から出していて、後ろの 4 バイトには触れていない。だから読む処理をいくら追っても、
この欄の意味は出てきません。答えがあったのは**書き出し側**でした。書き戻すときは
値を作らなければならないので、そこに「何を書くか」がそのまま現れます。

> 読む側は「使わない欄」を素通りできる。書く側は素通りできない。

分からない欄に当たったら、**その形式を書き出すコードがないかを先に探す**。これは
どの形式にも効く探し方です。

使い方も一手加えました。分かったからといって鵜呑みにはせず、**次の位置から出した長さと
突き合わせて、9 割以上一致したときだけ**長さとして使います。合っていれば、最後の項目を
詰め物ごと読まずに済みます (今までは末尾まで読んでいました)。合わなければ今までどおりの
読みに落ちるので、版によって違っても壊れません。診断にも
`位置表の長さの欄: 合う N 件 / 合わない M 件` を出すので、実物でこの読みが正しいかが
最初の報告で分かります。

ついでに、練習データの思い込みをもう 1 つ潰しました。練習データはこの 4 バイトを 0 の
まま書いていて、**実物と違う形**でした。第 9 節の「練習データが自分の思い込みを写して
いた」と同じ種類です。分からない欄を 0 で埋めた練習データは、その欄を使う読みを
一切試せません。

## 12. 黙って効かなくなる並び替え (#74)

抽出の側ばかり磨いていたので、校正の側を素人の目で頭から通してみました。わざと
間違えた訳文を食わせると、指摘の中身と文言は妥当でした。おかしかったのは**並び順**です。

最初の行の指摘が一番下に出ていました。原因は並び替えの鍵で、行の id を整数として
読もうとしていたのです。

いまの id は `diary#0:2` や `M_A01000:0-1` のような「ファイル名:表-行」の形なので、
整数として読むのは **必ず失敗**します。失敗したときは決め打ちの大きな値になる作りだった
ので、**全件が同じ値**になり、実際には severity と rule 名の順に並んでいました。

厄介なのは、落ちも警告もしないことです。並び替えは「それらしい順序」を返し続けます。
テストも「指摘が出るか」は見ていましたが「どの順で出るか」は見ていませんでした。

> 例外を握りつぶして決め打ちの値を返す並び替えは、壊れても動いているように見える。

id の形は途中で変わりました (通し番号 → ファイル名:表-行)。**形式を変えたときに、
その形式を前提にしていた場所を洗い出さなかった**のが元です。今回は行番号 (`_lineno`)
という、id の形に依存しない値がすでに手元にあったので、そちらで並べるようにしました。
外の形式に依存しない鍵を使う、という当たり前の形に落ち着いています。

検査も「出るか」だけでなく **「どの順で出るか」** を見るようにしました。

## 13. 緑の検査が、何も見ていないことがある (#81)

文書のコマンドが上から順に打てるかを見る検査を入れました (#80)。その次の回に
docs/08 で「最初の 1 行が落ちる」という、まさにその検査が捕まえるはずの誤りを
手で見つけました。検査は緑のままでした。理由は 2 つあり、どちらも同じ形をしています。

**1. 対象の選び方から、静かに外れる。** 検査は ```` ```bash ```` と印の付いた
囲みだけを読みます。docs/08 のコマンド囲みには印が無かったので、文書がまるごと
検査の外にいました。落ちるのではなく、**0 件を検査して「全部通った」と言う**わけです。

**2. 判定材料が、環境の汚れを拾う。** 「そのファイルは実在するか」を
`os.path.exists` で見ていました。`work/` は練習データを吐く作業場で、git には
入れていません。しかし生成器を一度でも走らせた環境では中身が埋まっています。すると
すべての練習ファイルが「実在する」と判定され、**前提の順序を一切見なくなります**。
まっさらな環境でしか効かない検査は、実質いつも効いていません。

もう 1 つ、判定を緩く書いたための素通しもありました。「文書のどこかに `make_elf.py`
と書いてあるか」で見たところ、別の段落で `hi_lo()` の説明のために名前を出していた
だけの箇所が拾われ、順序が逆のままでも通りました。**説明の中の名前と、打てる
コマンドは別物**です。`python3 tools/make_elf.py` のように打てる形だけを数えるようにしました。

> 検査を足したときは、**直す前の状態で赤くなること**を必ず自分の目で見る。
> 緑は「問題が無い」ではなく「問題を見つけられなかった」としか言っていない。

0 件を検査して通る失敗は特に見つけにくいので、対象の選び方が「印」や「命名」に
依存する検査では、**選べた件数そのもの**も疑ってかかります。

### 続き: 2 度目から通る壊れ方 (#82)

同じ型を探して e2e と node 側を見たら、一覧の抜けは無く、代わりにもっと悪いものが
出ました。まっさらに取得して検査を打つと **1 回目は落ちて、2 回目から通る**のです。
1 回目が練習データを作るので、2 回目はその残りで動きます。件数まで変わります
(115 件・失敗 1・飛ばし 4 → 116 件・全部緑)。

これは「もう一度走らせたら通ったから、たまたまだろう」で片付いてしまう形です。
実際には、練習データを作る順序 (材料の前後関係) が一覧から抜けていました。

厄介さを増していたのが**伝言の握りつぶし**です。呼ばれた道具は
「先に `python3 tools/make_sample.py` を実行してください」と、はっきり言っていました。
ところが呼ぶ側が `check=True, capture_output=True` で走らせていたため、その言葉は
捨てられ、`CalledProcessError` の traceback だけが出ていました。丁寧な伝言を書いても、
**呼ぶ側が捨てれば無い**のと同じです。

飛ばし (skip) も同じ穴でした。unittest は skip を「OK」の括弧に小さく足すだけなので、
取得直後の環境では 4 件が毎回飛び、そこでは一度も走らない検査になっていました。
作る道具は同じリポジトリにあるのだから、飛ばす前に作ればよい、というだけの話です。

> 検査は「自分の機械で通るか」ではなく **「取得したままの木で通るか」** で見る。
> 前回の残りに寄りかかった緑は、緑ではない。

直したあとは、まっさらな取得で 120 件・飛ばし 0 件・緑になりました。
