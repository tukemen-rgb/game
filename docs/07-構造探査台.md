# 構造探査台 — 構造が分からないファイルを読む

ここまでの道具は「構造が分かっているファイルを表示する」ものでした。
`web/` の構造探査台はその逆で、**構造が分からないファイルから構造を推定する**
ためのものです。ブラウザだけで動き、読み込んだデータはどこにも送信しません。

```bash
python3 tools/make_sample.py     # 疑似ゲームのファイル
python3 tools/make_iso.py        # それを詰めたディスクイメージ
open web/index.html              # そのまま開ける (Windows は start、Linux は xdg-open)

# 1 枚の HTML にまとめる場合 (練習用イメージも埋め込める)
python3 tools/build_web.py --embed-sample
```

## タブの一覧

画面の上に並ぶタブは 11 枚。**左から順に**、こういう役割です。
迷ったら「診断」に戻れば、次にどのタブへ行けばいいかが書いてあります。

| タブ | 何をする所 | 使いどき |
| --- | --- | --- |
| 診断 | 集めた手がかりから「このファイルはどう作られているか」を言葉にする。ほかのタブへの案内もここに出る | **最初に必ずここ。** 迷ったときも |
| 16 進 | 指定した位置から生のバイトを並べ、右に Shift-JIS / ASCII / UTF-8 / 読み込んだ表での読みを添える | 何かの先頭 16 バイトを報告するとき。ほかのタブが指した位置を自分の目で確かめるとき |
| 文字列 | 続けて読める文字の並びを拾う。最低文字数と、日本語 / ASCII の絞り込みが効く | 「このファイルに文が入っているか」をいちばん早く確かめたいとき |
| ポインタ表 | 値が単調に増えて全部ファイル内を指している並びを探す。表の直後から本文が始まるか、行き先の直前が区切りバイトか、の 2 つを根拠に確度を付ける | 文の位置を並べた表 (位置表) を見つけたいとき |
| 索引ファイル | 索引と本体の 2 つを渡して、本体をファイルに切り分ける (`BOKU2.IDX` / `BOKU2.IMG` はここ) | 僕の夏休み 2 の手順は、ここから始まる |
| 逆アセンブル | 本体プログラム (ELF) を MIPS R5900 の命令に直し、文字列への参照を拾う | 数字の意味 (1 行の字数など) を、プログラム側から裏付けるとき |
| 見つけた絵 | ファイル全体を走査して、絵らしい所を並べて出す | フォントや画像がどこにあるか当てが無いとき |
| タイル | 指定した位置を、1 ドットのビット数と幅を変えながら絵として並べる | 「見つけた絵」が拾い切れなかった絵を、手で合わせて出すとき |
| 相対検索 | 文字どうしの**差の並び**で探す。フォントが五十音順なら、文字コードの起点が分からなくても文章が見つかる | 文字コードがまったく未知のとき (清音のひらがなだけ・四文字以上がこつ) |
| 既知の形式 | 形が分かっているもの (TIM2・`.msg`・マップの入れ物…) として読む。校正用の TSV もここから | 形式の見当が付いたあと。**僕の夏休み 2 の本文はここで読む** |
| 調査メモ | 分かったことを書き留め、**報告用の要約**を作る | 社長に報告するとき。`→` の行はここにも出る |

## まず「診断」タブ

ファイルを選ぶと最初に出るのが診断です。集めた手がかりから
**「このファイルはどう作られているか」を言葉にします。**

判定だけでなく、**なぜそう言えるか**と、**そこで覚えること**を必ず添えます。
学習用の道具なので、答えより理由のほうが大事だからです。

練習用のデータを一通り読ませると、こうなります。

| ファイル | 診断 |
| --- | --- |
| `SCRIPT.BIN` | ポインタ表つきのテキストデータ |
| `MSG_ENC.BIN` | 独自の文字コードを使ったテキスト (推定) |
| `FONT.BIN` | 画像またはフォントのデータ |
| `RINFOLT.iso` | ディスクイメージ (ISO9660) |
| `SYSTEM.CNF` | ASCII のテキスト |
| `MOVIE.PSS` | 圧縮または暗号化されたデータ |
| `BGM.ADP` | 音声らしいデータ |
| `PAD.DAT` | ほとんどがゼロ埋め |

### 実物で判明した誤判定 — 乱数は日本語に見える

453MB の実データを読ませたとき、診断が「日本語テキストの塊」と出て、例に
`梳Hz噫_束` のような並びが挙がりました。**明確な誤りです。** 原因は 3 つ重なって
いました。順に潰した記録を残しておきます。

**1. 漢字ブロック全体を「よく使う範囲」に入れていた**

Shift-JIS の 2 バイト領域は漢字が大半を占めます。乱数がたまたま成立すると、
ほぼ必ず珍しい漢字の羅列になります。「常用の範囲か」だけで判定すると、
漢字ブロック全体が通ってしまって落とせません。

→ **仮名の割合**を見るようにしました。実際の日本語は仮名が半分前後を占めるのに
対し、乱数由来では 3% 程度です。仮名が 25% 未満の並びは捨てます。

**2. 半角カナが抜け穴になっていた**

`0xA1`〜`0xDF` は半角カナなので、乱数のバイトは 25% の確率でここに落ちます。
仮名の割合で数えていたため、半角カナだらけの並びが通っていました。

→ **全角の仮名だけ**を仮名と数えるようにしました。

**3. 波形の下り勾配が ASCII 文字列に見えていた**

`|xuqmiea]ZVROKG` — これは音声データの、値が単調に下がっていく部分です。
たまたま表示可能な ASCII の範囲を通過しているだけです。

→ 文字列側でいくら弾いても限界があるので、**そもそも走査しない**ことにしました。
圧縮・波形と分類された区画は文字列探索の対象から外します。**バイトの統計の
ほうが信用できる**という原則を、フィルタではなく走査範囲の設計に適用した形です。

この 3 つを直して、混在した 4MB のデータで測ると、検出件数は
24,961 件 → 14,400 件になりました。**14,400 は埋め込んだ実データの数と
ちょうど一致します** (1 ファイル 72 件 × 200 回)。例文も本物のセリフになりました。

### マスを細かくすると統計が壊れる

もう一つ踏みました。地図のマスを 64 バイトまで細かくしたら、圧縮データが
「タイル」に化けました。エントロピーは標本が少ないほど小さく出るので、
64 バイトでは乱数でも 5.1 程度にしかならず、しきい値に届かないためです。

→ **見た目のマスと、判定に使う窓を分けました。** マスは 64 バイト刻みのまま、
統計は最低 256 バイトの窓で取ります (マス同士が少し重なります)。

### 判定の順番が結果を決める

ここに実装上の落とし穴があります。**文字列の件数を先に見てはいけません。**

96KB の乱数データからは、Shift-JIS として偶然読めてしまう並びが数百件出ます。
件数だけで判定すると、圧縮データが堂々と「日本語テキストの塊」になります
(実際に一度そうなりました)。

**バイトの統計 (分類) のほうが、文字列の件数より信用できます。** なので
判定は次の順に見ます。

1. 決まった目印 (ELF、ISO9660)
2. 先頭のポインタ表 — あれば構造が確定する
3. **バイトの分類** — 高エントロピー / 波形 / ゼロ埋め
4. そのあとで文字列の件数

分類が「高エントロピー」や「波形」のときは、文字列の件数を根拠として出しつつ
**「偶然の一致とみられる」と明示します。** 数字を隠さず、意味を添える形です。

### 出している手がかり

* **先頭 4 バイトが読める文字か** — 自作形式でも名札を置くのが普通
* **バイトの並び順** — 32 ビット値を両方の並びで読み、小さい値として読めるほうを
  採る。ポインタや件数は小さい値になるため
* **ポインタ表の位置と境界** — 位置が 2048 の倍数に揃っていれば、読み込み単位に
  合わせているということ
* **別ファイルの索引が使えるか**
* **日本語が読めるか / 読めないか** — 読めないのに構造がある場合が独自文字コード
* **絵らしい領域**
* **制御コードらしいバイト範囲** — 文字コードが使っていない範囲に特定の値だけが
  繰り返し出るなら、それは改行や色替えの指示

| --- | --- |

| 2. 性質を地図にする | 一定の大きさごとにバイトの統計を取り、6 種類に色分けする |
| 3. 構造を推定する | 文字列の並び、ポインタテーブル、絵の領域を自動で探す |
| 4. 手で確かめる | 16 進、文字列一覧、タイル表示、相対検索 |
| 5. 分かったら読む | 形式が判明したファイルは本文まで展開する (索引・入れ物・会話・画像) |
| 6. コードを読む | 本体プログラム (ELF32 / MIPS R5900) を命令に戻し、文字列の参照元を辿る |

## 全体マップの読み方

一定の大きさのブロックごとに、ゼロの割合・表示可能文字の割合・Shift-JIS の
バイト対の割合・エントロピー・隣のバイトとの差を計算して分類します。

**上から順に見て、最初に当てはまったものに決まります。** 表の順番は、そのまま
判定の順番です。

| 順 | 色 | 意味 | 何を見て決めているか |
| --- | --- | --- | --- |
| 1 | 灰 | ゼロ埋め | ゼロが 92% を超える |
| 2 | 水 | 日本語テキスト | Shift-JIS の有効なバイト対が 45% を超える |
| 3 | 緑 | ASCII テキスト | 表示可能文字が 85% を超える |
| 4 | 橙 | 波形 (音声など) | エントロピーが 4.5 を超え、**かつ**隣のバイトとの平均差が 24 未満 |
| 5 | 桃 | 高エントロピー (圧縮・映像) | 標本が 192 バイト以上あり、エントロピーが乱数の期待値 −0.3 を超える |
| 6 | 藍 | タイル・コードなど | **上のどれにも当てはまらなかったもの** |

順番が効くところが 2 つあります。**橙は桃より先**なので、圧縮データでも隣との
差が小さければ橙になります。**藍はいちばん最後**で、独自の条件を持ちません
——「エントロピーが低いから藍」ではなく「他に当てはまらなかったから藍」です。
この順番のせいで階調のなだらかな絵が橙に取られるのが、
[取りこぼす絵](#この見つけ方が取りこぼす絵-なだらかな絵)の節の話です。

練習用イメージを開くと、この 6 種類がそのまま帯になって見えます
(全 1,312 区画の内訳: 桃 511・灰 444・橙 257・藍 85・水 11・緑 4)。
`MOVIE.PSS` が桃、`BGM.ADP` が橙、`PAD.DAT` が灰、`SCRIPT.BIN` が水です。

### エントロピーのしきい値を固定値にしてはいけない

ここに落とし穴があります。「エントロピーが 7.5 以上なら圧縮」のように
固定値で判定すると、**ブロックが小さいときに必ず外します。**

256 種類の値を n 個しか標本にしていないと、完全な乱数でもエントロピーは
log2(256)=8 に届きません。n=256 なら期待値は約 7.3、n=64 なら約 5.1 です。
なので標本数から「乱数だったときの期待値」を計算して、それと比べます。

```
期待値 ≒ 8 − 255 / (2n·ln2)
```

### セクタの詰め物を除く

ディスクイメージでは「80 バイトのテキスト + 1968 バイトのゼロ」が普通に
あります。そのまま平均を取ると何もかもゼロ埋めに見えるので、末尾の
ゼロを除いてから統計を取ります。

## ポインタテーブルの自動検出

このツールでいちばん価値があるのがこれです。人が 16 進を眺めて
「これはポインタ表だな」と判断するときの手がかりを、そのまま実装しています。

**まず候補を拾う** — 値が減らずに増えていき、すべてファイル内を指し、
1 件ずつの増分が現実的な並びを探します。16 ビットの表は値の範囲が狭く
偶然の単調増加ができやすいので、件数と増分の条件を厳しくします。

**基準の値は決め打ちにしない** — ポインタが何を基準にしているかは
ゲームによって違います。

* ファイル先頭からの絶対値
* テキスト領域の先頭からの相対値
* イメージの中に埋まったファイルの先頭からの相対値

そこで、いくつかの仮説を立てて総当たりし、あとから根拠で選びます。
仮説は「先頭の何件かは表の一部でない (別のヘッダ項目)」との組み合わせで
数通りです。

**根拠は 3 つ** —

1. **各行き先の直前が区切りバイト** — レコードが終端付きなら必ず `0x00` か
   `0xFF` が直前にある
2. **基準がセクタ境界** — 基準の値が 2048 の倍数 (0 は既定の仮説なので数えない)
3. **表の直後から本文が始まっている** — ただし**基準をそこに合わせていないとき
   だけ**数えます

2 つ以上そろったものだけを確度「高」にします。

### 当てはめた結果は証拠にならない

3 番目に条件が付いているのには理由があります。基準の候補には
**「1 件目がちょうど表の直後を指すような値」**が入っています。それが選ばれた
候補では、一致はいつも完全 —— **当てはめた結果を証拠として数える**ことに
なります。練習用イメージで数えるとこうです:

| | 件数 |
| --- | --- |
| 候補の総数 | 40 |
| ずれが 64 以下 (「表の直後から本文」の条件) | 36 |
| そのうち、基準をそこに合わせた候補 (ずれは必ず 0) | **18** |
| **ずれが 1〜64 の候補** (合わせていないのに惜しい) | **0** |

最後の行が要点です。**ずれは 0 か、まるで外れているかの二択で、その間が
ありません。** ずれ 0 の半分は当てはめて作った 0 なので、そのぶんは印に
なっていません。いまは合わせた候補では根拠に数えず、
「基準を当てはめれば表の直後から本文 (当てはめた結果)」という注記にしています。

この直しを入れる前は、40 件のうち **39 件**にこの印が付き、そのうち **38 件**が
当てはめたものでした。**ほぼ全部に付く印は、印になっていません。**

代わりに入れたのが 2 番目の**セクタ境界**です。当てはめて決めた基準が
たまたま 2048 の倍数になるのは珍しいので、当てはめと独立した印になります。
練習用イメージの 40 件のうち、これが付くのは **3 件**だけです。

**注記だけの候補も消しません。** 未知の形式を探す道具なので、黙って捨てず
確度「低」で残します。

### 波形データはどこで落ちるか

たまたま単調増加している波形データは、1 番目の根拠を満たしません。
合成した音 48KB を読ませると候補は 14 件出ますが、
**「行き先の直前が区切りバイト」が付くのは 0 件**です。
96KB の乱数にいたっては、候補そのものが 0 件です
(単調増加が必要な長さまで続かない)。

練習用イメージ (246KB) を丸ごと読ませると、**確度「高」はちょうど 2 件**
—— `SCRIPT.BIN` と `MSG_ENC.BIN` のポインタ表だけが出ます。ファイル形式を
何も教えていない状態で、ディスクの中のスクリプトを 2 つ見つけたことになります。

## 絵の自動検出 (「見つけた絵」タブ)

ポインタ表と並んで、この道具でいちばん気持ちがいい機能です。**位置も大きさも
指定せずに、絵が入っている領域を勝手に見つけて縮小図を並べます。**

手がかりは 2 つだけです。

1. バイトの性質が「タイル・コードなど」に分類される
   (圧縮・波形・テキストはここで落ちる)
2. **ある間隔だけ離れたバイトが、隣のバイトより似ている**

2 が本体です。画像は縦に相関があるので、1 行の長さだけ離れたバイトは似ます。
テキストや実行コードにはこの性質がありません。強さは

```
縦の相関 = (間隔をあけた平均差) ÷ (隣どうしの平均差)
```

で測り、1 より十分小さければ画像とみなします。練習用データで測ると

| データ | 分類 | 縦の相関 | 判定 |
| --- | --- | --- | --- |
| `FONT.BIN` (1bpp 16x16) | タイル | **0.59** | 絵 |
| `MSG_ENC.BIN` (独自コードの文章) | タイル | 0.99 | 絵ではない |
| `MOVIE.PSS` (圧縮相当) | 高エントロピー | — | 分類で落ちる |
| `BGM.ADP` (波形) | 波形 | — | 分類で落ちる |

とはっきり分かれます。しきい値は 0.82 にしてあります。

### この見つけ方が取りこぼす絵 (なだらかな絵)

上の手がかりは **1 の分類を通ってから 2 を測る**順です。だから
**1 で落ちた絵は、2 がどれだけ良くても拾われません。** 実際に取りこぼすのは
**階調のなだらかな絵** (写真・背景・グラデーション) です。合成データで測ると:

| ざらつき | 隣どうしの平均差 | 分類 | 縦の相関 | 見つけた絵に出るか |
| --- | --- | --- | --- | --- |
| 0 (なめらか) | 7.9 | 波形 | **0.73** | **出ない** (分類で落ちる。相関だけなら通る) |
| 36 | 23.2 | 波形 | 0.98 | 出ない (分類でも相関でも落ちる) |
| 64 | 36.8 | 高エントロピー | 0.93 | 出ない (分類でも相関でも落ちる) |

「ざらつき」は合成データを作るときの粒の大きさです。**作り方は
`tests/run_tests.py` の `TestTheBlindSpotOfTheImageFinderIsDocumented.gradient`**
にあり、この表の 3 行はそこで測り直しています。数字だけ書いて作り方を書かないと、
誰も確かめられません (この表は 2 行目・3 行目がまさにその状態でした)。

**本当の取りこぼしは 1 行目だけです。縦の相関 0.73 はしきい値 0.82 より小さい**ので、
そこまで辿り着けば「絵」と判定されます。それなのに、隣どうしの差が小さいという
理由で先に「波形」に分類され、測る前に落ちています。2 行目・3 行目は相関のほうも
しきい値を超えているので、**分類を緩めても拾えません**。

波形の判定は「エントロピーが高く、かつ隣との差が小さい」です。**色数の多い
なだらかな絵は、この 2 つを両方満たします。** 音声と見分けが付きません。

* **ドット絵やフォントは取りこぼしません。** 隣の差が大きい (輪郭がある) ので
  波形になりません。上の `FONT.BIN` が 0.59 で拾えているとおりです。
* **なだらかな絵を探すときは「見つけた絵」に頼らないでください。**「タイル」
  タブで位置と 1 行の長さを手で指定すれば、そのまま見られます。
  1 行の長さは 16・32・64・128 あたりを順に試すのが速い道です。

### では、緩めたら何が起きるのか (測った)

「波形の分類を外して、音にも相関を測りにいく」とどうなるか。長いあいだ
**「音声ファイルが軒並み『絵』として出てきます」**と書いていましたが、
測ったら**そこまでひどくはありませんでした**。合成した音で見ると:

| 音の周期 | 分類 | いちばん小さい縦の相関 | 分類を外したら絵として出るか |
| --- | --- | --- | --- |
| 16 バイト | 波形 | **0.13** | **出る** |
| 24 バイト | 波形 | **0.29** | **出る** |
| 32 バイト | 波形 | **0.52** | **出る** |
| 23 バイト | 波形 | 1.02 | 出ない |
| 128 バイト | 波形 | 7.93 | 出ない |
| `BGM.ADP` (練習データの音) | 波形 | **7.94** | 出ない |

**練習データに入っている音そのものは、緩めても絵になりません。** しきい値の
10 倍近く離れています。危ないのは**周期が候補の刻み (8・16・24・32・64・128) と
ちょうど合う音だけ**で、23 バイト周期のように合わない音は出てきません。

理由ははっきりしています。**なめらかな波では、相関の値は「間隔そのもの」に
近づきます。** 局所的にはただの坂なので、間隔を 8 空ければ差は隣どうしの約 8 倍。
だから、いちばん短い候補 (8) でも相関は 8 前後になり、しきい値 0.82 には
まるで届きません。低い音ほど安全側です。

そのうえで、この一式は今も「出したものは確からしい」側に倒してあります。
守っている相手は**刻みに合う高めの音**という狭い範囲ですが、対価 (1 行目の
取りこぼし) も狭い範囲なので、釣り合いは取れていると判断しました。
取りこぼしは手で拾えて、誤検出は数が多いと手に負えないためです。
**「軒並み出てくる」は言い過ぎでした。測らずに書いた言葉が 32 回分残っていました。**

### ゼロ同士の組を数えない

ここに落とし穴があります。**ゼロ埋めはどの間隔でも完全に一致する**ので、
素朴に平均差を取ると詰め物のある領域が「周期が強い」と誤判定されます。
セクタの詰め物は至るところにあるので、これを直さないと使い物になりません。
両方がゼロの組は数から除いています。

この修正を入れる前と後で、ディスクイメージ全体を読ませた結果はこう変わりました。

```
修正前: 手前の別データを巻き込んで、1 つ手前のセクタから始まる
修正後: 0xE800 から 10.0 KB ← FONT.BIN の実際の位置 (0xE800, 10,656 バイト)
```

報告する大きさが 10,656 バイトちょうどにならないのは、領域の端を **512 バイト刻み**で
寄せているからです。位置のほうは、その刻みで詰め物を落とし切るので実際の先頭と合います。

### 繰り返しの周期の見当 (「見当を付ける」ボタン)

「タイル」タブの **「見当を付ける」** は、いくつかの刻み
(2・4・8・16・24・32・48・64・96・128・256 バイト) で
「その分だけ離れたバイトがどれくらい合うか」を測り、
いちばん合った刻みを **1 タイルのバイト数**として使います。

**正解の分かる 8 通りで数えたら、1/8 しか当たりませんでした。**
外し方が 2 つありました。

**1. 周期が無くても 1 位が出る。** 並べ替えれば必ず先頭は決まるので、乱数でも
「繰り返しの周期が強い順: 96 バイト …」と出ていました。候補どうしの差は 1% 程度
—— **並びは中身ではなく誤差**です。

**2. 本物の周期があっても、その倍数が同じ点を取る。** 8 バイト周期のデータでは
16・32・64… も同じだけ合うので、1 位はしばしば 128 や 256 になります。
それを 1 タイルの大きさとして使うと、**絵が何枚も 1 枚に潰れて**出ます。

直したのは 2 段です。

* **強さ** = (いちばん悪い点 − いちばん良い点) ÷ いちばん悪い点。
  小さければ「どの刻みでも同じ」= 周期なしと言い切ります。
* **倍数も合うことを求める。** 本物の周期 P なら 2P・3P… も合うはずです。
  良い側に入った刻みのうち、**自分の倍数がすべて良い側に入っている最小のもの**を
  採ります。見つからなければ 1 位に戻ります。

| データ | 正解 | 強さ | 直す前 (1 位) | 直したあと |
| --- | --- | --- | --- | --- |
| 合成タイル 8 バイト | 8 | 0.43 | 128 | **8** |
| 合成タイル 16 バイト | 16 | 0.42 | 128 | **16** |
| 合成タイル 32 バイト | 32 | 0.41 | 256 | **32** |
| 合成タイル 64 バイト | 64 | 0.41 | 256 | **64** |
| 合成タイル 128 バイト | 128 | 0.40 | 256 | **128** |
| `FONT.BIN` (実物) | 32 | 0.29 | 32 | **32** |
| 乱数 | 周期なし | 0.01 | 96 | **周期なし** |
| ゼロ埋め | 周期なし | 0.00 | 2 | **周期なし** |

**1/8 → 8/8。** 合成データは**1 タイルごとに絵を変えて**作っています
(同じ絵を並べると、どんな見方でも当たってしまって検査になりません)。
作り方は `tests/run_tests.py` の `TestThePeriodGuessIsCounted` にあります。

周期が読めないときは、ボタンは**数字を入れません**。
「はっきりした繰り返しが見つからないので、見当を付けられませんでした」と言い、
1 行の長さを手で試すよう案内します。**当てずっぽうを設定として見せない**
ためです。

### 1 ドットのビット数の見当

1 タイルのバイト数から 1 辺を逆算するので、まず 1 ドットが何ビットかを決めます。
**ここは当たり外れがあります。6 通りの絵で数えると 4 通りしか当たりません。**

| 絵 | 正解 | 見当 |
| --- | --- | --- |
| `FONT.BIN` (実物のフォント) | 1bpp | 1bpp |
| 疎なドット絵 | 1bpp | 1bpp |
| 背景が 0 のスプライト | 8bpp | 8bpp |
| 色数の多い絵 | 8bpp | 8bpp |
| 16 色の絵 (2 画素/バイト) | 4bpp | **8bpp** |
| 32 色しか使っていない絵 | 8bpp | **4bpp** |

**外すのは決まって 4bpp と 8bpp の取り違えです。** 色数で当てにいっていますが、
4bpp を 2 画素ずつ詰めると**バイトの値は 256 種類まで広がる**ので、
16 色の絵でも「色数が多い」に見えます。逆に 8bpp でも実際に使う色が少なければ
4bpp に見えます。**バイトを見ただけでは、この 2 つは分けきれません。**
縮小図に出る「4bpp」「8bpp」は見当で、押せば「タイル」タブで手で切り替えられます
(どちらが正しいかは、絵が出た瞬間に目で分かります)。

#### 1bpp かどうかは、平坦さだけでは決められない

以前は「`0x00` と `0xFF` が 3 割を超えていれば 1bpp」とだけ見ていました。
それだと**背景が 0 で埋まった 8bpp のスプライト** —— 市販ゲームでいちばん多い形
—— が平坦 85% で 1bpp と判定され、**1 辺まで倍に外れて**いました
(16×16 を 32×32 と報告)。

分けるのは平坦さではなく、**隣のバイトとの跳ね方**です。1bpp のバイトは
ビットの模様なので大きく跳ね、絵のバイトは隣どうし似ています。

| 絵 | 隣のバイトとの平均差 |
| --- | --- |
| `FONT.BIN` (実物のフォント) | 57.7 |
| 疎なドット絵 | 28.5 |
| 16 色の絵 (2 画素/バイト) | 16.4 |
| 色数の多い絵 | 13.9 |
| 背景が 0 のスプライト | 1.7 |
| 32 色しか使っていない絵 | 1.0 |

1bpp の 2 つと、それ以外の 4 つの間がはっきり空いています。いまは
**「平坦が 3 割超、または色が 16 種以下」かつ「隣との平均差が 22 を超える」**を
1bpp の条件にしています。この直しで、上の表の当たりが 2/6 から 4/6 になりました。

**推定は入口で、確定は人が行う**という組み立てです。

## 独自文字コードのファイル

`MSG_ENC.BIN` はマップ上で「タイル・コードなど」に分類されます。
**独自文字コードのテキストは、バイトの統計では画像やコードと区別できません。**
これは限界ではなく事実で、だから相対検索が必要になります。

1. 相対検索のタブで「ここは」などの清音のかなを探す
2. ヒットを押すとテーブルが下の欄に入る
3. 「このテーブルを 16 進表示に使う」を押す
4. 「既知の形式」のタブに、かなの部分が読める本文が出る

漢字と記号はまだ `・` のままです。ここから手でテーブルを育てていく作業に
なります → [02-相対検索.md](02-相対検索.md)

## 別ファイルの索引 (「索引ファイル」タブ)

市販ゲームで最も多い「索引 + 本体」の組 (`BOKU2.IDX` と `BOKU2.IMG` のような対) を
読みます。レコード長・位置の列・長さの列・単位を総当たりし、**位置が減らずに
増える / 本体をはみ出さない / 本体をだいたい使い切っている** で採点します。

分かっている形は当てにいかず、そのまま読みます。僕の夏休み 2 の `DFI` 形式が
その例で、レコードの直後にレコード順で並ぶ名前と、`+2` の「まだ続くか」で
フォルダの入れ子を復元します (根拠は [09](09-調査ログと引き継ぎ.md))。

切り分けた結果は左の一覧にぶら下がります。名前が読めなかったものは
**中身を見て種類を末尾に付けます** (`#0012.tm2` / `#0345.packed`)。魔法数
(TIM2 / VAGp / RXWS / ELF …) で当たれば確実、無ければ見当です。
一覧の上の **絞り込み欄** に `msg` や `.tm2` と入れると、それだけが並びます。

### 見当が当たるかを数えた

練習用の `BOKU2SAMPLE` は組み立て方が分かっているので、**20 件の正解が
手元にあります**。数えたら **11/20** しか当たっていませんでした。しかも
外していたのは、よりによって**探している当のもの**です。

| 取りこぼしていたもの | 何と出ていたか | なぜ |
| --- | --- | --- |
| `.msg` 4 件 | 不明 (タイル・表など) | **入れ物を指す呼び名が一つも無かった** |
| 入れ物 4 件 (日記・保存画面・出来事・釣り) | 不明 (タイル・表など) | 同上 |
| `bk_font.tms` | 不明 (タイル・表など) | 魔法数を**先頭だけ**で見ていた |

この道具で名前の無いファイルに見当を付ける目的は
「1951 個の中から**テキストを探す**」ことなのに、**テキストの入れ物を指す
言葉が無かった**わけです。絞り込み欄に `msg` と入れても 1 件も出ませんでした。

直したのは 2 つ。

* **入れ物の形を見る。** u32 の件数、位置が増えていき、どれもファイル内、
  そして**1 件目の位置が表の直後**。`.msg` は表の直後がそのまま本文
  (刻み 8 か 4)、日記などの入れ物は表の後ろを 16 バイト境界まで詰めてから
  部品が始まります (刻み 8 か 12)。空き枠 (位置も長さも 0) は飛ばします。
  当たれば `msg` / `parts` と名前が付きます。
* **前置きの後ろの TIM2 を探す。** 実物のフォントは 0x80 の前置きつき
  ([11](11-形式を突き止めるまで.md))。英語化パッチの公開ソースも `findTIM2s` で
  ファイル全体から `TIM2` の 4 バイトを探しています。先頭で当たれば確実、
  途中で見つけたものは見当、と分けます。

これで **20/20**。**入れ物かどうかを、埋まっている TIM2 より先に見ます** ——
中に絵が 1 枚あるだけで「画像」と名づけると、
**同じ入れ物に入っている文章が見えなくなる**からです
(`diary.bin` がまさにその形: 0 番が日記の文、1 番が写真)。

緩めた代償も測りました。練習用イメージを 512 バイトごとに 4KB の窓で 485 回、
乱数 4KB を 200 窓——**どちらも 0 件**です。「1 件目が表の直後」は
読み取った値そのもので、当てはめて作った一致ではないので効きます
([当てはめた結果は証拠にならない](#当てはめた結果は証拠にならない)と同じ話)。

解析のあとに出る **「報告用の要約を作る」** は、索引・本体・`.msg`・フォント・MAP を
一通り診た文章で、本文 (セリフ) を含みません。`tools/boku2.py check` と同じ行が
出るので、どちらで作っても報告に使えます。**締めの 1 行上に「診ていない段: N 件」が
出ることがあります** —— 「問題なし」は「全部を診た結果」ではなく「診た分には問題が
無かった」という意味なので、何を診ていないかはそこで数えて出します。行のうち決め手になるもの:
`DFI: 期待どおり` / `名前が付いた N 件` / **`フォルダの規則: 2 通り (stack / flag) で一致`**
(フォルダの閉じ方には、こちらの規則と英語化パッチの公開ソースの規則の 2 通りがあり、
両方で道筋を作って突き合わせます。食い違えば件数と例が出るので、その行ごと報告。
**一致のときは「フォルダの中のファイル N 件で突き合わせた」と分母が付きます**。
入れ子の無い索引では 2 通りに差が出ないので、そのときは「試せていない」と出ます) /
`[フォント] … 512×… 画素` / `[文字表] 貼ってある文字表: N 字 / … 文字表に無い K 種`
(「.msg として読む」の欄に文字表を貼ってから作ると、先頭 50 件の `.msg` 全体で
あと何字足りないかが出る。貼っていなければ「まだ貼っていない」) /
`位置表の長さの欄: 合う N 件 / 合わない M 件` (8 バイト刻みの後ろ 4 バイトが、本当にその項目のバイト長かの突き合わせ。合わなければ位置だけで読むので壊れないが、その行ごと報告してほしい) / `[MAP] … 会話 M 行`。外れた所は `→` で示し、先頭の 16 バイトを添えます。**索引が読めなくても要約は作れます** (むしろ読めないときこそ報告する材料が要るため)。その場合は先頭 64 バイトと「ここで止めました。この先は診ていません」だけの短い要約になります。

## 分かった形式を読む (「既知の形式」タブ)

「分かったら読む」の段階です。判明した形式を 1 つずつ足していく場所で、いま
読めるのは次のとおり。

| 形式 | 何が出るか |
| --- | --- |
| SCRP (練習用) | ヘッダ・ポインタ表・本文 (テーブルがあれば独自コードも復号) |
| TIM2 (PS2 の標準画像) | 正しい色と大きさで描画。32/24/16bit と 4/8bit 索引、`.tms` の前置きに対応。**「文字の番号を重ねる」**でフォント画像に番号を振れる。既定は刻み 22 ドット (実機の描画ルーチンと同じ。枠は 23 で 1 ドット重なる)、列数は画像の幅から自動 (僕の夏休み 2 は 1 行 23 字)。**1 つのファイルに TIM2 が 2 枚以上あれば、位置の釦で切り替えられる** (文字表は 1 枚に収まらないので、続きがここにあることがある)。**2 枚目以降の番号は前の頁の続きから振る** (0 から振り直すと文字表が丸ごとずれる)。**自動で出た列数が 23 でなければ ⚠ を付けて言う** —— この作品には 1024 ドット幅の画像があり、渡すと 23 字ではなく 46 字ずつ番号が振られる。ずれても出てくる字は日本語のままなので、目では気づけない。直前に読んだ `.msg` で使われている字は **緑の枠**、そのうち文字表にまだ無い字は **橙の枠**。**「文字表の下書きを作る」** は、各マスの形と、同じ大きさで描いた候補の字の形を突き合わせて `番号=文字` の下書きを入れる (仮名・数字・記号のみ。漢字は手で足す)。**当たりは保証しない下書き**で、人が書いた分は上書きしない。当てたあと **並び順**でも直す (続いたマスが続いた字なら、その区間は五十音の並びで埋め直す。区間を外へ伸ばすときは画像で裏を取る)。実測は形だけで 81%、並び順を足して 93%。**候補は仮名・数字・記号が既定**なので、漢字などは「下書きの候補に足す字」の欄に貼る (実測: 漢字 8 字は貼らないと 0 字、貼ると 7 字当たった) |
| 僕の夏休み 2 の `.msg` | 件数・位置表・本文。フォントの文字の並びを貼れば日本語に。要約に「使われている番号 N 種」と **「文字表に無い番号 K 種 (例: …)」** (または「文字表で全部読める」) が出る。表が複数の会話ファイル、見出しの無い並び (0x8000 区切り)、Shift-JIS の並び (0x00 区切り) も自動で見分ける。`item_info.msg` など 7 つのメニューでは 0x8002 が引数の無い **ページ送り** (`{BREAK}`) で、ファイル名で見分ける |
| マップの入れ物 | 「マップの入れ物を切り分ける」で `0.bin, 1.bin …` に。会話は `1.bin`。部品を読んで「これはマップの入れ物です」と出たら **入れ物の中の入れ物** (`fish_on_mem.bin` の 11〜16 番など) なので、その部品を選んだまま **もう一度切り分ける** (一括処理の `text` は自動で降りる) |
| LZSS (奥村版) | 今の位置から伸張を試す / 全体から伸張できる場所を探す |

`.msg` を読んだあとの **「校正用の TSV をコピー」** で、docs/04 の校正ツールに
そのまま渡せる形 (`id / offset / size / original / translation`) になります。
実物での通し手順は [10-僕夏2の手順.md](10-僕夏2の手順.md)。

## 本体プログラムを読む (「逆アセンブル」タブ)

ELF を選ぶと、ヘッダ・読み込み区画・セクションを出したうえで、
入口から MIPS の命令に戻して並べます。`jal` や分岐の行き先はクリックで
飛べます。

いちばん使うのは **「文字列を使っている場所を全部探す」** です。
MIPS は 32 ビットのアドレスを 1 命令で作れないので、住所は必ず
`lui` (上位 16 ビット) + `addiu` / `ori` (下位 16 ビット) の 2 命令に割れます。
この組を全域で追いかけると、**どの文字列をどのコードが使っているか**の
一覧ができます。ファイル名やエラーメッセージが並んでいる場所の周りが、
たいてい読み込み処理です。

詳しくは [08-コードを読む.md](08-コードを読む.md)。

## 人に見せる (「調査メモ」タブ)

ここまでに分かったこと (位置・分類・根拠) を、そのままコピーして人に渡せる
文章にします。解析は画面の中だけで完結していてデータはどこにも送られないので、
相談したいときは、この文章を自分で渡す必要があります。ファイルそのものは
含みません。

## 誤検出について

推定は推定なので、外れます。とくに圧縮データや乱数のような領域では、
偶然 Shift-JIS として読める並びが必ず混ざります。減らし方は 2 段構えです。

**1 段目 — そもそも見ない。** 全体マップで「圧縮・乱数」か「波形」と分類された
区画は、文字列の走査そのものをしません。**これがいちばん効きます。** 96KB の
乱数を読ませると 96 区画すべてが「高エントロピー」になるので、画面に出る
文字列は **0 件**です。バイトの統計のほうが信用できる、という原則の適用です。

飛ばしたことは画面に出します (「文字列」タブの上の行)。**黙って 0 件と出すと、
道具が壊れているのと見分けが付きません。**

**2 段目 — 読めた並びを捨てる。** 見た区画の中では、次の 4 つで落とします。
96KB の乱数を**わざと 1 段目を外して**走査し、条件を 1 つずつ抜いて測った
「その条件だけが落としている件数」を添えます (最低文字数は既定の 6)。

| 捨てる条件 | この条件だけが落とす件数 |
| --- | --- |
| 2 バイト文字のうち**仮名の割合**が 25% 未満 (4 字以上のとき) | **208 件** |
| 割り当てのないコード (U+FFFD になるもの) を含む | 20 件 |
| よく使う範囲 (かな・常用漢字・全角記号) の割合が 60% 未満 | 1 件 |
| 英字の偏り (英字 6 字以上かつ全角の 1.5 倍超) | 0 件 |

**効いているのは仮名の割合だけです。** Shift-JIS の 2 バイト領域は漢字が
大半なので、「よく使う範囲か」だけでは漢字ブロック全体が通ってしまい、
ほとんど落とせません。実際の日本語は仮名が半分前後を占めます。

4 つ全部を外すと 1,686 件、全部入れて **およそ 1,100 件**。つまり
**2 段目で減るのは 3 分の 1 ほど**です。残るのは
`"?r_z7V"` `"%Bzｪ(_=㎝B"` のような、**ASCII の短い並びに半角カナや漢字が
くっついたもの**で、これは 2 バイト文字が 3 つに満たないため日本語の条件が
そもそも掛かりません。**ゼロにはできません。**

だから確度の根拠を画面に出して、最後は人が判断できるようにしてあります。
「自動で全部分かる」と見せるツールのほうが、かえって使えません。

> 数字はすべて `tests/run_tests.py` の `TestHowManyFalsePositivesSurvive` で
> 測り直しています。乱数の作り方もそこにあります。

## 画面の設計

見た目は「分光板」という一つの考えでまとめています。

**画面上で彩度を持つのはデータだけ。** クロームはインク 1 色系に落とし、六種の
色相だけが色として残るようにしています。そうするとバイトマップが分光プレートの
ように読め、どこに何があるかが一目で入ってきます。逆に、装飾に色を使うと
データの色と競合して読めなくなります。**情報設計として色を空けておく**という
判断です。

参照しているのはこの系統です。

| 系統 | 何を採ったか |
| --- | --- |
| Binary Ninja / IDA / ImHex | 密度と等幅。数字は等幅数字 (tabular-nums) で桁を揃える |
| binvis.io / Veles | バイトマップを主役に据える構え |
| 計測器のパネル (Tektronix など) | 目盛り・十字線・下端の読み取り帯 |
| 日本の理工書の組版 | ヘアライン罫で区画を作り、枠線を減らす |

意識して避けたもの: near-black にアシッドグリーンひとつ (この分野で最も擦られて
いる)、紫から青のグラデーション、角丸カードに左アクセントバー。

### 決めごと

* **色の指定は必ずトークン経由** (`--cls-jp` など)。明暗の切り替えは
  `prefers-color-scheme` と `data-theme` の両方で効かせる。明側は「印刷された板」、
  暗側は「計測器」として別に設計してあり、単純な反転ではない
* **朱 (`--seal`) は要点だけ。** 確度「高」、選択中のファイル、現在のタブ、
  ブランドマーク。それ以外には出さない
* **角丸は使わない。** 区画はヘアライン罫で作る
* **区画の見出しは等幅・大文字・字間広め** (`.eyebrow`)。日本語の本文と
  役割が混ざらないようにするため
* **番号 (01〜06) は順序が意味を持つところだけ。** 解析は本当に六段階の
  手順なので振っている。並列な項目には振らない
* **動きは一回だけ。** 読み込み時にマップを左から掃く。散らすと安っぽくなる。
  `prefers-reduced-motion` で無効化する

### 実装で踏んだ罠

* `.intake { display: grid }` が `hidden` 属性に勝ってしまい、画面が切り替わらなかった。
  `[hidden] { display: none !important }` が必要
* ヒーローの幕を `::after` で敷いたら本文の上に来た。`z-index` を明示しないと
  疑似要素が中身を覆う
* HTML のソースで日本語を折り返すと、その改行が半角空白として表示される。
  文の途中で改行しないこと

## ここから育てるなら

`web/app.js` は 1 本の素の JavaScript で、節ごとに分かれています。
機能を足すときの入口はこのあたりです。

| やりたいこと | 触る場所 |
| --- | --- |
| 別の入れ物 (PAK / AFS など) を開く | `readIso` の隣に同じ形の関数を足し、`openFile` から呼ぶ |
| 判定の種類を増やす | `CLASSES` と `classifyStats` |
| 別の構造を探す | `findPointerTables` と同じ形の関数を足し、`selectEntry` から呼ぶ |
| 分かった形式を読む | `renderFormat` の分岐 (`renderScrp` / `renderTim2` が例)。作品固有の読みは `bokumsg` ブロックのように `@extract-start` で囲み、Node のテストから切り出せるようにする |
| 分かっている索引をそのまま読む | `readDfi` の隣に同じ形の関数を足す (`{ entries }` を返せば `namedEntries` がそれを使う) |
| 画像形式の対応 | `decodeTim2` に画素の種類を足す。推定表示は `drawTiles` |
| 絵の検出を強くする | `tileScore` の手がかりと `TILE_RATIO_MAX` |
| 命令の対応を増やす | `MIPS_OPS` / `MIPS_SPECIAL` / `MIPS_MMI` の表 (追加したら `node tests/test_disasm.mjs`) |

テストは `python3 tests/run_tests.py` が全部まとめて回します。ブラウザ側のコードは
`@extract-start 名前` 〜 `@extract-end 名前` で囲んだ塊を Node に切り出して
突き合わせています (`tests/test_index.mjs` / `test_disasm.mjs` / `test_lzss.mjs` /
`test_sniff.mjs` / `test_bokumsg.mjs` / `test_tim2.mjs` / `test_fuzz.mjs` = 壊れたデータで
例外を投げないこと)。ブラウザ本体の動き
(読み込み → 索引 → 切り分け → .msg → 文字表 → TSV) は `tests/e2e/` の検査が
ヘッドレスブラウザで実際に操作して確かめます (`python3 tests/e2e/run_all.py`。
`build.py` は組み立てた単体 HTML そのものを開き、練習用イメージが読めて外部への
要求が無いことを見る。
playwright が無ければ飛ばします)。

いちばん伸ばしがいがあるのは **「分かった形式を読む」** の部分です。
解析ツールというのは、推定の機能を増やすよりも、判明した形式の読み取りを
1 つずつ足していくことで実用的になっていきます。
