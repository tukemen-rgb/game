# 文字テーブル — どのバイトがどの文字か

コンピュータの中に「文字」は存在しません。あるのは数値だけです。
その数値と文字の対応表が **文字テーブル** (キャラクタテーブル、`.tbl`) です。
ゲームのテキストを扱う作業は、ほぼ全部ここから始まります。

## 先に練習データを作る (最初に一度だけ)

この文書のコマンドは `work/` の練習データを使います。まだ無ければ作ってください
(自作の架空データなので、権利の心配はありません)。

```bash
python3 tools/make_sample.py     # work/SCRIPT.BIN, MSG_ENC.BIN, FONT.BIN
```

作り忘れたまま打つと、道具が「練習データはまだ作られていません」と、
作るコマンドまで出して止まります。

## パターン 1: 標準の文字コード (Shift-JIS)

日本の PS2 ソフトでいちばん多いのがこれです。OS やライブラリが持っている
コード表をそのまま使うので、バイナリエディタで開けば日本語がそのまま見えます。

```bash
python3 tools/hexdump.py work/SCRIPT.BIN --message 2
```

```
0000013D  F1 01 F4 00 81 49 81 40 82 B1 82 F1 82 C8 82 C6  «NAME»«VAR»！　こんなと
0000014D  82 B1 82 EB 82 C9 82 A2 82 BD 82 CC 82 CB 81 42  ころにいたのね。
0000015D  F0 82 B8 82 A2 82 D4 82 F1 92 54 82 B5 82 BD 82  «BR»ずいぶん探したの
0000016D  CC 82 E6 81 42 F2 FF                             よ。«WAIT»«END»
```

読み方の要点:

* `82 B1` = 「こ」、`82 F1` = 「ん」。ひらがなは `82 9F`〜`82 F1` に **連番** で
  並んでいます。この連番性が次章の相対検索の土台になります。
* 2 バイト文字の 1 バイト目 (先頭バイト) は `81`〜`9F` と `E0`〜`EF` の範囲だけ。
  だから 1 バイト目を見れば「この文字は 1 バイトか 2 バイトか」が判定できます。
* `92 54` = 「探」。漢字も同じ 2 バイトの並びに入っています。

### Shift-JIS だと分かったら

それ以上やることはありません。Python なら `data.decode("cp932")`、HxD なら
表示エンコードを Shift-JIS に切り替えるだけです。校正作業に入れます。

## パターン 2: 独自の文字コード

一方、ゲームが自前の並びを持っていることもよくあります。理由は単純で、

* フォントに入れる文字を絞れば ROM/ディスクの容量が減る
* 1 バイトで済ませれば、テキストのデータ量が半分になる
* 制御コードを好きなバイト値に置ける

`work/MSG_ENC.BIN` がこのパターンです。テーブルを知らずに Shift-JIS として
開くと、意味のない文字の羅列になります。

```bash
python3 tools/hexdump.py work/MSG_ENC.BIN --message 2                       # 読めない
python3 tools/hexdump.py work/MSG_ENC.BIN --message 2 --table answers/custom.tbl  # 読める
```

このファイルのテーブルは次のような設計になっています (`answers/custom.tbl`)。

```
0x01-0x53  ひらがな (ぁ〜ん)      … 1 バイト、Unicode 順の連番
0x54-0xA6  カタカナ (ァ〜ン)      … 1 バイト、連番
0xA7-0xB0  全角数字 (０-９)
0xB1-....  記号 (。、「」！？…など)
0xE0 xx    漢字                   … 2 バイト。xx が漢字テーブルの番号
0xF0-0xFF  制御コード
```

かなを 1 バイトにして、使用頻度の低い漢字だけ 2 バイトに逃がす、という
容量重視の設計です。実際のゲームでもよく見る形です。

## パターン 3: フォント画像の並び順が、そのままテーブル

3 つ目があります。**表を持たない**やり方です。本文のバイトは
「フォント画像の何番目の文字か」という**通し番号**で、番号と文字の対応は
画像そのものにしかありません。

これは机上の話ではありません。この一式が実物として扱っている
僕の夏休み 2 (PS2) がこの形でした (docs/09・docs/10)。番号は 2 バイトで、
フォント画像は 1 行 23 字・刻み 22 ドット、文字表は全部で 1656 字。

素人がここで足を止めるのは、**探しても出てこない**からです。
Shift-JIS で検索しても出ませんし、相対検索 (docs/02) の道具もそのままでは使えません
—— あちらは **1 バイトの連番**を探す作りだからです。

ただし**考え方のほうは効きます**。英語化パッチの公開ソースに残っている
この作品の文字表を見ると、かなは `ぁあぃいぅう…` と五十音順に並んでいました。
つまり「かなが連番なら、差が一定の並びを探せばいい」という相対検索の理屈は
そのまま当てはまり、足りないのは**2 バイトで探す道具**のほうです。
この一式は別の道 (フォント画像を見て表を作る) を取ったので、そこは作っていません。

見分け方は 3 つ:

* バイト列が **小さい 2 バイトの数**ばかりで、Shift-JIS の 1 バイト目
  (`81`〜`9F` / `E0`〜`EF`) の規則に合わない
* 同じ作品の中に**文字の絵が並んだ画像**がある (TIM2 など)
* 画像のマスの数と、本文に出てくる番号の最大値が**だいたい合う**

練習データで、同じファイルを表なしと表ありで読んでみます。

```bash
python3 tools/make_boku2_sample.py
python3 tools/boku2.py unpack work/BOKU2SAMPLE/BOKU2.IDX work/BOKU2SAMPLE/BOKU2.IMG work/BOKU2OUT
python3 tools/boku2.py text work/BOKU2OUT/system
python3 tools/boku2.py text work/BOKU2OUT/system -f work/BOKU2SAMPLE/font.txt
```

```text
system:0	0x24	12	[55][32][73][19][81]	[55][32][73][19][81]
system:0	0x24	12	はじめから	はじめから
```

`[55]` は「フォント画像の 55 番目のマス」という意味です。ここに何の字が
描いてあるかは、**画像を見るまで誰にも分かりません**。だから作業は
「画像のマスを 0 番から順に書き写して表を作る」ところから始まります。
それが `font.txt` で、この文書で言う文字テーブルそのものです。
構造探査台には、マスの形から下書きを当てる手伝いもあります (docs/10 の手順 6)。

書き写した `font.txt` は、この文書の `.tbl` にも変換できます。

```bash
python3 tools/boku2.py table work/BOKU2SAMPLE/font.txt -o work/boku2.tbl
```

```text
190 件 → work/boku2.tbl  (例: python3 tools/hexdump.py system.msg --table work/boku2.tbl)
```

こうすると `hexdump.py --table` で 16 進表示のまま日本語が読めます。
**パターン 1〜3 のどれであっても、行き着く先は同じ「番号と文字の対応表」**です。

## .tbl ファイルの書き方

ROM ハックの世界で昔から使われている、素朴な行指向の形式です。

```
# コメント
01=ぁ
02=あ
E000=一
```

`tools/scrp.py` の `load_table()` がこれを読みます。2 バイト以上のコードも
書けて、デコードのときは長いものから優先して照合します。

## 制御コードは「文字ではないバイト」

セリフの中には、文字以外の指示が混ざっています。

| バイト | タグ表記 | 意味 |
| --- | --- | --- |
| `F0` | `<BR>` | 改行 |
| `F1 xx` | `<NAME:xx>` | 話者名テーブルの参照 |
| `F2` | `<WAIT>` | ボタン入力待ち |
| `F3 xx` | `<COLOR:xx>` | 文字色の変更 |
| `F4 xx` | `<VAR:xx>` | 変数の差し込み (プレイヤー名など) |
| `F5` | `<CLEAR>` | ウィンドウのクリア |
| `FF` | — | メッセージの終端 |

`F0` 以降に置いてあるのには理由があります。Shift-JIS の 2 バイト文字の先頭
バイトは `81`〜`9F` / `E0`〜`EF` なので、そこと重なるバイト値を制御コードに
使うと「制御コードなのか漢字の一部なのか区別できない」データになってしまいます。
**制御コードは、その文字コードが使っていないバイト範囲に置く。** これは
自分でフォーマットを設計するときにも効く原則です。

パターン 3 の実物でも、同じ原則がそのまま使われていました。僕の夏休み 2 の
文字番号は 1656 までしか無いので、制御コードは**そこよりずっと上**に置いてあります。

| 2 バイトの値 | タグ表記 | 意味 |
| --- | --- | --- |
| `0x8000` | `{END}` | メッセージの終端 |
| `0x8001` | `<BR>` | 改行 |
| `0x8002` + 数 | `<WAIT:xx>` | 待ち時間 (次の 2 バイトが引数) |
| `0xCDCD` | — | 4 バイト境界までの詰め物 |

文字の番号は 0x0000〜0x0678 の範囲に収まるので、`0x8000` 以上を見た時点で
「これは文字ではない」と決められます。**1 バイトのときと同じ考え方が、
2 バイトでもそのまま効く**という例です。

なお 2 バイト文字の 2 バイト目 (トレイルバイト) には `F0` 以降が出てきます。
`♪` は Shift-JIS で `81 F0` です。1 バイト目で長さが決まるので実害はありませんが、
「`F0` を見たら改行」と決め打ちで書いたツールはここで壊れます。実際の
ROM ハックでよく踏むバグです。

## 抽出したテキストの表し方

制御コードを含むテキストを TSV や Excel で扱うために、このリポジトリでは
`<BR>` のようなタグ表記に置き換えています。バイト列とタグ表記は 1 対 1 で
往復できます (`tests/run_tests.py` がそれを検証しています)。

文字としての `<` は `<LT>` と書きます。生の改行・タブは使えません。
